# V1.6 - Extracted Knowledge Processing

The first processing layer between EXTRACTED PDF PAGES
(`maintenance_document_pages`, V1.5) and STRUCTURED MAINTENANCE KNOWLEDGE
(`maintenance_knowledge_entries`/`machine_error_codes`, V1.3). Deterministic
only - no LLM/AI, no external API, no fabricated solutions. The extracted
PDF text remains the source of truth; this milestone only detects
candidates and hands them to a mandatory human review step before anything
reaches the live knowledge base.

## 1. Real-document discovery (read-only, patterns only)

Before writing any detection code, the real Production Konica extraction
(121.8MB source, 2639 pages, `maintenance_document_pages` for document
`c4587c91-29a7-460c-8ef5-84f2e199c142`) was sampled read-only via aggregate
SQL queries and a small number of short (~150 char) structural excerpts -
never a full page, never committed anywhere. Findings:

- Page text length: 34-43,907 chars, average ~2,219 chars/page. No empty
  pages.
- **`C-DDDD` (a literal dash, exactly 4 digits, e.g. "C-2451") is the real
  troubleshooting-code format.** Each distinct dash-coded token appears on
  only 1-5 pages - the signature of a real code appearing at its own
  definition plus a table-of-contents/cross-reference line. 62+ distinct
  dash-coded tokens were observed in the sampled range.
- **`CDDDD` (no dash) is NOT an equivalent representation of the same
  thing.** It is the machine model number: `C1070` alone appeared on 2,454
  of 2,639 pages (93%) as a running header/footer. Other bare tokens
  (`C8000`, `C7000`, `C6501`, ...) appeared dozens of times each - other
  model/series numbers referenced in cross-sections, not error codes. This
  directly contradicts the naive assumption that "C-2801 / C2801 / C 2801"
  are interchangeable formatting of the same code - real detection must
  never treat the dash as optional.
- The table of contents lists codes as dotted-leader lines
  ("2.16.13 C-2451....................") with no cause/action text nearby -
  a real, common false-positive shape the detector must down-rank.
- Section markers actually present in the document: "Cause" (579 pages),
  "Troubleshooting" (507), "Detection" (395), "Action" (70), "Remedy" (0).
  None are universal, so their presence is genuine signal.

No manual passages are reproduced above or anywhere in this milestone's
code/tests/commits - only counts, token shapes, and structural patterns.

## 2. Detection and normalization (`app/Services/KnowledgeProcessing/`)

- `ErrorCodeNormalizer::detectCandidates()` matches only the dash form
  (`\bC\s*-\s*(\d{4})\b`, tolerating spacing variants like "C - 2451") -
  never bare `C\d{4}`, per the false-positive evidence above.
- `ErrorCodeNormalizer::normalize()` is separately lenient (accepts a
  dash-optional value) so collision detection can compare against
  `machine_error_codes.code` values that predate this milestone and may
  have been typed by hand without a dash - detection and comparison are
  deliberately different strictness levels for different reasons.
- `PdfKnowledgeCandidateDetector` classifies each match's evidence as
  **HIGH** (a strong marker - Cause/Action/Countermeasure/Remedy - appears
  in the match's bounded context window), **MEDIUM** (only a weak marker -
  Troubleshooting/Detection - nearby, or a strong marker exists elsewhere on
  the page), or **LOW** (no marker nearby, or the match sits inside an
  obvious TOC dotted-leader line). No fabricated percentage.
- `title` falls back to a plain "Error Code C-XXXX" whenever the text
  immediately following a match does not look like a real short heading
  (the common case - most matches are TOC/index lines). `description` is a
  short (~440 char) bounded excerpt around the match, for human review only
  - never treated as an authoritative summary.
- `operator_solution`/`technician_solution` are **intentionally never
  populated** by the detector. Reliably splitting real cause text from real
  corrective-action text in arbitrary manual prose is not something a fixed
  regex can do without risking fabrication - left for human review before
  publish, per Section R's explicit instruction never to fabricate.

## 3. Data model - purely additive, no parallel tables

Reuses V1.3's `maintenance_document_imports`/`maintenance_knowledge_entries`
lifecycle wholesale. A `PDF_EXTRACTION` import IS one deterministic-detector
processing run over one extraction, distinguished from `MANUAL_ENTRY` only
by carrying `extraction_id` and `processing_*` metadata. One migration
(`2026_09_22_000100_add_pdf_processing_fields_to_maintenance_knowledge.php`)
adds:

- `maintenance_document_imports`: `extraction_id`, `processing_started_at`,
  `processing_completed_at`, `pages_processed`, `candidate_count`,
  `processing_version`.
- `maintenance_knowledge_entries`: `extraction_id`, `normalized_code`,
  `source_page_start`, `source_page_end`, `evidence`, `collision_status`,
  plus the `maintenance_knowledge_entry_identity_uq` unique index on
  `(import_id, normalized_code, source_page_start, source_page_end)`.

## 4. Idempotency (Section I)

Two layers, both deterministic:

1. **Run identity**: `startProcessing()` is idempotent by
   `(document_id, extraction_id, processing_version)` - calling it twice
   for the same completed extraction returns the same import row rather
   than starting a second, competing processing run. A later extraction
   (new `extraction_id`) always gets its own, distinguishable import.
2. **Candidate identity**: within one import, `firstOrCreate()` on
   `(import_id, normalized_code, source_page_start, source_page_end)` means
   re-running the same chunk (a genuine reprocessing attempt, or a retried/
   duplicated queue job after an interruption) only ever creates entries
   that do not already exist - it never updates an existing row. This is
   also why human-reviewed/published candidates are never silently
   overwritten: the identity key never changes underneath an existing row,
   and the write path for that key is skip-if-exists, not upsert.

## 5. Chunked, resumable queue processing (Sections M/N)

`ProcessMaintenanceKnowledgeJob` processes one bounded page range per
invocation (default 100 pages) and dispatches the next chunk itself when
more remain - never all 2639 pages in one job, never inside an HTTP
request. Runs on the same `database`/`default` queue V1.5.6 already proved
Hostinger cron drains automatically; no new queue infrastructure, no second
cron entry. `pages_processed`/`candidate_count` are written as absolute
values (a fresh `MAX(page_number)` bound and an actual `COUNT()`), not
increments, so a retried chunk is always safe.

**Performance** (synthetic dataset matching the real document's shape -
2639 pages, ~2200 chars/page average, dash-codes on ~16% of pages, matching
the real 428/2639 sample ratio - never real Konica content):

| Metric | Result |
|---|---|
| Total processing time (all 2639 pages, 27 chunks of 100) | 0.25s |
| Average chunk time | 9.3ms |
| Max chunk time | 13.7ms |
| Peak memory delta | ~2MB |

All comfortably within the V1.5.6 worker bounds (`--timeout=300s`,
`retry_after=420s`, runner `--max-time=50s`, `--max-jobs=25`) - with
`--max-jobs=25`, the entire real document would finish within roughly two
cron ticks (~10 minutes) once dispatched.

## 6. Collision classification (Section J)

Computed once, at candidate creation time, against
`machine_error_codes` scoped to the same `(account_id, machine_model_id)`:

- **NEW**: no existing code matches the candidate's normalized code.
- **POTENTIAL_UPDATE**: a match exists, but it has no
  `manufacturer_description`/`official_solution` yet, and this candidate's
  evidence is HIGH (found near real Cause/Action text) - a deterministic
  signal that this candidate may carry more complete information than
  what is currently published.
- **EXISTING**: a match exists and already carries description/solution
  content.

Never auto-resolved and never auto-published - always a human review
signal shown alongside the candidate (Section Q/R).

## 7. Provenance (Section K)

Every candidate retains `document_id` (via `import.document`),
`extraction_id`, and `source_page_start`/`source_page_end`. Publishing
(unchanged `MaintenanceKnowledgePublishService`, reused as-is) creates a
`maintenance_document_reference` row carrying the real source page number -
verified directly in `MaintenanceKnowledgeProcessingTest::
test_publishing_an_approved_candidate_reuses_the_existing_publish_service_and_retains_provenance`.
No page text is duplicated into the published record beyond the bounded
review excerpt already on the draft entry.

## 8. Deliberate scope decisions

- No cause/action text splitting - see Section 2 above.
- No new controller: the one new endpoint
  (`POST /maintenance/documents/{document}/process-knowledge`) lives on the
  existing `MaintenanceKnowledgeImportController`, reusing its
  authorization (`AccountAccessResolver::canManageCatalogScope`), its
  entry review/publish endpoints (`updateEntry`/`publishEntry`) completely
  unchanged, and its capability gate.
- No `CACHE_STORE`/queue/cron change of any kind - this milestone is
  implementation-only, not deployed.
- Frontend: extends the existing Knowledge Import UI (Document Detail →
  Knowledge imports → the existing list/detail dialogs) rather than a new
  module - a "Process Knowledge" trigger, real progress text, and
  evidence/collision badges plus a filter row on the existing candidate
  list.
