# V1.9 - Source Page Context for Knowledge Review

## 1. Problem

The real, human-reviewed C-1127 publish (V1.8/V1.8.1's acceptance) needed more than the
per-candidate `description` field the review UI already showed: `KnowledgeCodeGroupQuery::detail()`
deliberately returns only "the stored bounded excerpt, exactly as the candidate row holds it...
No page text." To correctly attribute which troubleshooting/DIPSW block belonged to C-1127's
PK-512/513 variant versus its PK-522 variant (and to confirm pages 32/949 were legitimately
table-of-contents / SC-code lookup noise, not real diagnostic content), the actual review had to
bypass the product entirely and read `maintenance_document_pages.raw_text` directly via SQL. That
is not an acceptable normal workflow for the 704 remaining code groups. The application already
stores the necessary text; V1.9 is purely a read-only surface for it.

## 2. Data source

No new table, no migration. `maintenance_document_pages` (`document_id`, `page_number`,
`raw_text`, unique on `(document_id, page_number)`) already holds the complete extracted text of
every page. V1.9 reads it directly - it is never duplicated, denormalized, or copied elsewhere.

## 3. Authorization boundary

Reuses the exact same boundary as every other Knowledge Review read: `codeGroup()`'s
`readableImport()` gate (`import->document->account_id` against the caller's active memberships,
platform Superuser bypass for a null/global scope). A page is looked up by
`document_id = $import->document_id` - the same document the already-authorized import belongs
to - so a page from a different document (and therefore a different account) can never be
returned; there is no separate page-level permission to get wrong. This is fail-closed by
construction, not by a frontend check: an unauthorized `document-imports/{id}/...` request 404s
before any page query ever runs.

## 4. API contract

**Extended, not duplicated**, per the existing "one place per fact" convention:

- `GET /api/v1/maintenance/document-imports/{id}/code-groups/{code}` (existing endpoint) - the
  response gains two additive fields, `source_pages` and `source_pages_truncated`. Every existing
  field is unchanged; existing callers ignore fields they don't ask for.
  ```
  source_pages: [
    { page_number: 1460, raw_text: "...", is_primary: true },
    ...
  ]
  ```
  `is_primary` distinguishes a page that is some occurrence's actual detected
  `source_page_start` from a page only present because it falls inside another occurrence's
  `start..end` span (rare - see 5).

- `GET /api/v1/maintenance/document-imports/{id}/code-groups/{code}/pages/{pageNumber}` (new,
  read-only) - ONE adjacent context page beyond the group's own direct source pages, for the case
  a procedure continues across a page break (the real C-1127 review needed page 1459, one before
  1460, and pages 1462-1463, one/two after 1461). This is deliberately **not** a generic page
  reader: a requested page is refused (404, indistinguishable from "does not exist") unless it is
  within `ADJACENT_PAGE_MAX_DISTANCE` (3) pages of one of the group's own source pages. The
  response's `is_direct_source` flag tells the caller whether the page turned out to already be
  one of the group's own pages.

## 5. Page-range semantics

Each occurrence's own `source_page_start..source_page_end` is real provenance and is expanded in
full (e.g. `1460..1461` yields both pages). Two safety bounds, both justified from real
Production data (2639 pages, 2680 candidates, 705 groups) rather than guessed:

- `MAX_OCCURRENCE_PAGE_SPAN = 20` - caps one occurrence's own range (mirrors
  `KnowledgeGroupPublisher::MAX_RANGE_SPAN`). Real data never exceeds a span of 1.
- `SOURCE_PAGE_LIMIT = 40` - caps the total distinct pages returned for one group, after
  dedup across every occurrence in the group. The worst case actually observed across all 705
  real groups is 8. A group's actual `source_pages_truncated` flag is set (and the page set
  deterministically truncated ascending) only if this is ever exceeded, e.g. by malformed data.

A page an occurrence cites but that has no matching `maintenance_document_pages` row is simply
omitted (not an error, not a fabricated placeholder).

## 6. Payload bound

Measured directly against the real document (2639 pages): average page ~2.2 KB, max observed
~44 KB, C-1127's own 4-page group totals ~13 KB. `detail()` fetches page text in exactly one bulk
query (`whereIn('page_number', ...)`, single `document_id`), never per-page, never the full
2639-page extraction for one review action - confirmed by a dedicated backend test asserting
constant query count regardless of how many source pages a group has.

## 7. Frontend behavior

`SourcePageContext` (inside the existing `CodeGroupDetailDialog`, right after "Supporting
evidence") shows one active page's full text at a time, with a compact page-number selector when
a group has more than one source page, plus Previous/Adjacent Page navigation that calls the
adjacent-page endpoint lazily and clearly labels a result "Direct source page" vs. "Adjacent
context page." Text reuses the existing `.maintenance-extracted-page` convention
(`white-space: pre-wrap`, plain `<p>`) already used by the document extraction viewer, so line
breaks and wrapping behave identically. An optional, deterministic highlight of the group's own
normalized code is an exact string split rendered as ordinary React children (`text.split(code)`,
`<mark>`) - never a regex over meaning, never AI, never HTML from raw content.

## 8. Security behavior

- No `dangerouslySetInnerHTML` anywhere; raw extracted text is always rendered as React text
  children.
- The adjacent-page endpoint cannot be used to browse a document: distance-bounded to the
  requesting group's own evidence, and every lookup is scoped to the already-authorized
  `document_id`.
- Nothing about this feature is exposed without the same account/tenant check every other
  Knowledge Review read already requires.

## 9. No-mutation guarantee

Reading source page context touches none of `maintenance_knowledge_entries`,
`machine_error_codes`, `maintenance_error_solutions`, `maintenance_document_references`,
`maintenance_document_imports`, or `maintenance_document_pages` itself, and writes no
`governance_audit_logs` row (consistent with existing policy: reads are not audited). A dedicated
backend test asserts a full before/after snapshot of every one of those tables is byte-identical
after exercising both endpoints. Nothing here ever populates or overwrites a canonical `title`,
`description`, operator guidance, or technician solution - source context is evidence for the
human reviewer only, exactly as before.
