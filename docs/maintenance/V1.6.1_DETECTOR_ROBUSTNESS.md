# V1.6.1 - Detector Robustness & Review Quality

Closes the gap the real V1.6 Production acceptance run exposed: a genuine
UTF-8 boundary bug that only real manual text (never the ASCII-only
synthetic test fixtures V1.6 shipped with) could trigger, plus a real
review-usability gap once a real 1285-candidate import existed.

## 1. The UTF-8 fix

Root cause (already proven before this milestone, not rediscovered here):
`PdfKnowledgeCandidateDetector::boundedContext()`/`deriveTitle()` sliced
context with byte-oriented `substr()` at an arbitrary fixed radius
(+/-220 bytes). Real manual text's legitimate multi-byte Unicode
punctuation (curly quotes, em/en dashes, bullets, degree signs, accented
Latin) can land in the middle of that radius, producing a truncated,
invalid UTF-8 byte sequence - which MySQL correctly rejected with
`Incorrect string value: '\xE2'` on `description` (already `utf8mb4` -
never a charset/schema problem).

Fixed by expressing every arbitrary radius/length in **characters**, never
bytes, via `mb_substr()`/`mb_strlen()`. `preg_match`'s `PREG_OFFSET_CAPTURE`
offsets are byte-based even for a non-`/u` pattern, but converting one to a
character offset via a plain `substr()` prefix cut is safe specifically
because `ErrorCodeNormalizer`'s pattern only ever matches pure ASCII (`C`,
`-`, digits, whitespace) - an ASCII byte can never be a UTF-8 continuation
byte, so cutting a valid UTF-8 string right before one can never split a
character, regardless of what precedes it.

A distinct, separately-handled case: `toValidUtf8()` only ever rewrites a
string that fails `mb_check_encoding()` to begin with (stripping invalid
byte sequences via `iconv('UTF-8','UTF-8//IGNORE', ...)`) - it never
touches text that was already valid, which is the entire class of string
this bug actually mishandled. A slicing bug and a corrupt-input problem are
two different failure modes and are never conflated.

Audited the rest of the V1.6 processing path (`MaintenanceKnowledgeProcessingService`,
`ProcessMaintenanceKnowledgeJob`, `MaintenanceKnowledgeImportController`,
`GovernanceAudit`) for the same class of byte-boundary risk around
`description`/`evidence`/`title`/`operator_solution`/`technician_solution`/
audit metadata - none exist outside `PdfKnowledgeCandidateDetector.php`
(`evidence`/`collision_status` are fixed short ASCII enum values the code
itself controls, never PDF-derived text; `title`/`code`/`normalized_code`
are short regex-derived tokens with no radius-based slicing).

## 2. Review usability at real scale

The real V1.6 run produced 1285 candidates in a single import before it
failed - a volume `MaintenanceKnowledgeImportController::show()` never
anticipated (it eagerly loaded every entry into one response). Fixed:

- `show()` no longer embeds `entries` at all - it returns the import's own
  metadata plus a new `evidence_summary` (a single grouped-aggregate query:
  `SELECT evidence, COUNT(*) ... GROUP BY evidence`, real DB counts, never a
  fabricated percentage).
- A new `GET /maintenance/document-imports/{id}/entries` endpoint lists
  candidates **server-paginated** (mirrors the existing
  `MaintenanceDocumentExtractionController::pages()` convention exactly)
  and **server-filtered** by `status`, `collision_status`, `evidence`, and
  `code` (search) - all applied in SQL via `where()`, never fetched in full
  and filtered in the frontend, so pagination totals stay truthful for the
  filtered set.
- The frontend (`KnowledgeImportDetail`) gained an Evidence filter
  (All/HIGH/MEDIUM/LOW) alongside the existing status/collision filters and
  code search, all composing together in one request
  (`useKnowledgeEntries`), plus a compact real-count evidence summary and
  Previous/Next pagination controls (reusing the existing extracted-pages
  viewer's pagination CSS/pattern).

## 3. No migration

`evidence`/`collision_status` were already stored columns since V1.6 - no
schema change needed for filtering itself. `maintenance_knowledge_entries`
already carries a `(import_id, status)` composite index (V1.3). A query
filtering by `import_id` (always present - every entries request is scoped
to one import) plus `evidence`/`collision_status` uses that index to narrow
to at most one import's row count first; even the real Production import's
1285 rows is a trivially small in-memory scan after that narrowing (real
row counts this small do not need or benefit meaningfully from a dedicated
per-column index). No migration was added.

## 4. What was deliberately NOT changed

Per Section G: no LOW candidates were discarded, no page-number hacks for
the dense pages 30-38/946-952 regions, no global Cause/Action requirement,
no invented confidence percentages, no auto-publish, no AI/LLM
classification. Candidate-*quality* tuning (whether the detector should
treat dense index/glossary regions differently) remains a distinct,
evidence-driven decision for a later milestone, informed by a complete real
run - which this milestone's fix makes possible for the first time.
