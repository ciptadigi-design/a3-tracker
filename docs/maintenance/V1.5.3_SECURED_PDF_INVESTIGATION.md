# V1.5.3 - Secured/Encrypted PDF Fallback Investigation

## Root cause (production)

Real production acceptance testing on `31f3178` uploaded a genuine Konica Minolta
Troubleshooting Code Guide PDF, readable by the user in any normal PDF viewer.
Extraction failed with:

```
Secured pdf file are currently not supported.
```

thrown from `Smalot\PdfParser\Parser::parseContent()`
(`vendor/smalot/pdfparser/src/Smalot/PdfParser/Parser.php:106`):

```php
if (isset($xref['trailer']['encrypt']) && false === $this->config->getIgnoreEncryption()) {
    throw new \Exception('Secured pdf file are currently not supported.');
}
```

The PDF's trailer dictionary carries a `/Encrypt N G R` entry - a standard PDF
security handler (this is extremely common even for PDFs with no open password;
many PDF producers apply an owner-password-only "restrict editing/printing"
encryption by default, which still fully encrypts the content streams the parser
needs to read). This is **not** a memory, queue, storage, or worker-connectivity
problem - every step up to and including the parse call succeeded; the parse call
itself hit a real format limitation of the parsing library.

## Does `ignoreEncryption` help?

No. `Smalot\PdfParser\Config::setIgnoreEncryption(true)` only skips the guard
above - it does not add a decryption engine. Inspecting the installed
`smalot/pdfparser` v2.12.5 source (`vendor/smalot/pdfparser/src/Smalot/PdfParser/`)
confirms there is no RC4/AES cipher implementation anywhere in the library, so
setting this flag would not yield readable text for standard-security-handler
encrypted content - it would just replace a clear "unsupported" error with silent
garbage/binary output, which fails goal J.10 ("Do not fake successful extraction").
`ignoreEncryption` is left off.

## Constraints (real production environment)

- Hostinger shared hosting: no Supervisor, no persistent worker process
  (`docs/hostinger/HOSTINGER_QUEUE_SETUP.md`).
- **`shell_exec()` is disabled in the production PHP CLI environment** (confirmed
  in production, not assumed). `exec`, `system`, `proc_open` cannot be assumed
  available either.
- No OS binary can be relied on: no `qpdf`, no `pdftotext`/Poppler, no
  Ghostscript, no Python, no Docker.
- PHP 8.2, Laravel 11, Composer-only dependency management.

These rule out every common "decrypt with a binary, then re-parse" approach
(`qpdf --decrypt`, Ghostscript re-distilling, `pikepdf`/Python, etc.) outright -
none of them are installable or invokable in this environment.

## Pure-PHP alternatives considered

| Library | Verdict | Why |
|---|---|---|
| `setasign/fpdi` (+ `fpdi-pdf-parser`) | Rejected | Built for importing/merging pages into a *new* PDF via TCPDF/FPDF, not text extraction; does not decrypt standard-security-handler content either. |
| Raising `smalot/pdfparser`'s own `ignoreEncryption` flag | Rejected | No decryption engine exists in the library (see above) - would silently produce garbage instead of a clear failure. |
| Hand-rolling RC4/AES-V2/V4/V5 PDF decryption in-house | Rejected for V1.5.3 | Technically pure-PHP and thus Hostinger-compatible, but a correct implementation (key derivation per PDF spec Algorithm 2/2.A, per-object key salting, AES-CBC with padding, permission-password vs user-password handling) is a substantial, security-sensitive undertaking on its own - not something to bolt onto a UX/reliability release. A real candidate for a dedicated future phase, not this one. |
| Any actively-maintained, license-compatible pure-PHP library that both decrypts standard PDF encryption *and* extracts text | None found | No such library was identified during this investigation that meets all of: PHP 8.2 compatible, no OS binary dependency, actively maintained, license compatible with this project, and page-level text extraction (not just page rendering/rasterization). |

## Outcome for V1.5.3

Per the task's explicit instruction ("If no suitable proven fallback exists, DO NOT
force one into this release"), **no secured-PDF decryption fallback ships in
V1.5.3**. Instead:

1. `SmalotPdfTextExtractor` classifies this exact failure mode as
   `UNSUPPORTED_PDF_SECURITY` (`PdfExtractionErrorCode`) - a **permanent**
   classification (see `ExtractMaintenanceDocumentJob`), so the job does not waste
   retry attempts on a failure retrying cannot fix.
2. The extraction lifecycle ends truthfully as `FAILED` with that error code and a
   safe, specific user-facing message - the PDF itself remains stored and
   available for viewing/download; only knowledge extraction is blocked.
3. The `PdfTextExtractor` interface (`app/Services/PdfExtraction/`) is the seam a
   future engine - either a vetted pure-PHP decryption implementation, or an
   out-of-process service reached over HTTP instead of a local binary - would
   implement, without `DocumentExtractionService` or `ExtractMaintenanceDocumentJob`
   needing to change.

## Practical mitigation available today (no code change)

Most PDF viewers/editors (including free ones) can re-save a copy of a
restrictively-encrypted-but-viewable PDF without that encryption once opened with
read access. Re-uploading such a resaved copy would extract normally under the
existing Smalot-based pipeline. This is an operational workaround, not something
this release automates or exposes in the UI.
