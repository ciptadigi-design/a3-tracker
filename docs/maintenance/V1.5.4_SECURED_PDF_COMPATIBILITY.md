# V1.5.4 - Secured PDF Compatibility Research

Research-only milestone. **No decryption was implemented, no code path in
`DocumentExtractionService`/`ExtractMaintenanceDocumentJob` changed, and
Production was never mutated** (read-only SSH: `stat`, `sha256sum`, a
checksum-verified copy to a local, gitignored scratch directory for
analysis - never committed, never modified in place). This document is the
evidence base V1.5.5 will be designed from.

## 1. Executive Summary

The real production Konica Minolta document
(`bizhub_PRESS_C1070_C1070P_C1060_PRO_C1060L_E_SM_v1.5.pdf`, 121,833,361
bytes) uses the **PDF Standard Security Handler, revision 4, AES-128
(`/CFM /AESV2`)**, with an **empty user password** (confirmed valid - the
document opens with no password prompt in any compliant reader) and an
owner-only restriction on editing/copying. This is one of the most common
"protected" PDF profiles in the wild (Adobe Acrobat's classic "restrict
editing" with 128-bit AES, produced here by Antenna House's PDF Output
Library). `smalot/pdfparser` v2.12.5 (this project's only extraction engine)
has **zero decryption capability of any kind** - not a missing feature flag,
an entirely absent code path - so it refuses the file outright with
`"Secured pdf file are currently not supported."`, exactly reproducing
V1.5.3's classified `UNSUPPORTED_PDF_SECURITY` outcome.

The cryptographic primitives this profile needs (AES-128-CBC, MD5) are
already present in PHP's bundled `openssl`/`hash` extensions on every PHP
install, including Hostinger shared hosting - **no external binary, no
shell_exec, no FFI, no root is required to decrypt this exact profile**. The
missing piece is PDF-spec-specific key-derivation logic (ISO 32000-1
Algorithm 1/2/5), which is a well-documented, deterministic, reviewable
algorithm - not a fundamental blocker, and (see section 7) no longer
something this project would have to hand-roll from a blank page: credible
existing PHP implementations were identified during this research that did
not exist, or were not found, during V1.5.3's investigation.

A new read-only `PdfSecurityInspector` (`app/Services/PdfExtraction/`) can
classify this exact profile - and confirm the empty password - using
Smalot's own already-battle-tested raw parser, with zero new PDF-tokenizer
code and zero decryption capability of its own. A synthetic, sanitized
fixture reproducing the identical security profile is now committed at
`backend/tests/Fixtures/pdf-security/`, so this classification behavior is
regression-tested without the real document ever being committed.

## 5. Cipher Requirements

Minimum cryptographic behavior a future decryptor needs for exactly this
profile (R=4, AESV2, `/StmF`=`/StrF`=`/StdCF`):

1. **Password padding** (Algorithm 2 step a): pad/truncate the password to
   32 bytes using the fixed PDF padding constant
   (`28 BF 4E 5E 4E 75 8A 41 ...`). For the empty password this is just the
   32-byte constant itself.
2. **File encryption key derivation** (Algorithm 2): `MD5(padded_password ||
   O || P_as_4_bytes_LE || ID[0] [|| 0xFFFFFFFF if R>=4 and
   EncryptMetadata=false])`, then (R>=3, which R=4 always is) re-hash the
   result 50 times, truncating to the key length (16 bytes here) each
   iteration.
3. **Document ID involvement**: yes - `/ID[0]` is required input to Algorithm
   2; a document with no `/ID` cannot be authenticated this way at all
   (this project's `PdfSecurityInspector` returns `null` rather than
   guessing when `/ID` is absent).
4. **Permissions value involvement**: yes - `/P` (the signed 32-bit
   permission bitmask) feeds directly into the file-key hash; it is not
   merely advisory metadata for reader UI.
5. **User-password authentication** (Algorithm 5 for R>=3): re-derive the
   file key, compute `RC4(fileKey, MD5(padding || ID[0]))`, then apply 19
   further RC4 passes each re-keyed with `fileKey XOR byte(k)` for
   `k=1..19`, and compare the first 16 bytes against `/U`. This exact
   19-pass loop is the step most naive implementations get wrong or skip.
6. **Object-number/generation-specific keys** (Algorithm 1): per object,
   `MD5(fileKey || objNum_as_3_bytes_LE || genNum_as_2_bytes_LE || "sAlT"
   if AES)`, truncated to `min(len(fileKey)+5, 16)` bytes. The literal ASCII
   `"sAlT"` suffix applies **only** for AES crypt filters (Algorithm 1.A) -
   omitting it is a common, silent correctness bug.
7. **AES object decryption**: content is `IV(16 bytes) || ciphertext`;
   decrypt with AES-128-CBC using the per-object key from step 6 and that
   IV. PHP's `openssl_decrypt(..., 'aes-128-cbc', $key, OPENSSL_RAW_DATA,
   $iv)` already strips PKCS#7 padding automatically - no manual padding
   logic needed.
8. **PKCS#7 padding**: handled by `openssl_decrypt` itself for AES (see
   above); RC4 has no padding (stream cipher) and is not needed for this
   specific document, only for revisions 2/3 or `/CFM /V2`.
9. **Crypt filters**: `/StmF` and `/StrF` must both resolve through `/CF` to
   the same `/CFM /AESV2` filter for this document - a correct
   implementation must also *reject* (not silently misinterpret) split
   filter configurations or `/Identity` filters it does not support, exactly
   as `PdfSecurityInspector` does not attempt to.
10. **`EncryptMetadata` handling**: absent here (defaults `true`), so
    metadata streams are encrypted like any other stream and decrypt the
    same way - no special case needed for this specific document, but a
    real implementation must still read the flag rather than assume it.

This is section-by-section identical to ISO 32000-1 7.6.3 Algorithms 1, 2,
and 5 - nothing here is Konica-specific; it is the generic Standard Security
Handler R2-R4 algorithm, characterized against this real document's actual
field values.

## 6. Smalot Limitation

`Smalot\PdfParser\Parser::parseContent()`
(`vendor/smalot/pdfparser/src/Smalot/PdfParser/Parser.php:106`, v2.12.5)
rejects unconditionally:

```php
if (isset($xref['trailer']['encrypt']) && false === $this->config->getIgnoreEncryption()) {
    throw new \Exception('Secured pdf file are currently not supported.');
}
```

This check runs **after** `RawDataParser::parseData()` has already
successfully parsed the file's xref/trailer/object structure (confirmed by
inspection and by this milestone's new `PdfSecurityInspector`, which calls
`RawDataParser::parseData()` directly and never hits this guard) - so the
rejection is a deliberate library-level policy decision, not a genuine
parsing failure. A fresh `grep -rli "rc4|aes|cipher|decrypt"` over the
installed `smalot/pdfparser` source (re-run for this milestone, same result
as V1.5.3) finds no cipher implementation anywhere in the package; the one
match (`AEsmall` in `PostScriptGlyphs.php`) is an unrelated font-glyph name
("Æ small caps"), not an AES reference. Raising
`Config::setIgnoreEncryption(true)` only removes this guard - it does not
add decryption, and would silently hand back the raw *encrypted* byte
strings as "extracted text" (binary garbage), which V1.5.3 correctly
rejected as "faking successful extraction."

## 8. Integration Options (Smalot integration analysis, section H)

Given Smalot has zero decryption capability and the rejection happens before
any object is decoded:

- **Option A - decrypt to a private temp file, then hand it to the
  existing, unmodified `SmalotPdfTextExtractor`.** A new extractor
  (implementing the same `PdfTextExtractor` interface) authenticates the
  empty password, walks the already-parsed raw object/xref structure
  (reusing `RawDataParser` exactly as `PdfSecurityInspector` already does),
  decrypts each string/stream in place using a library from section 7 (or
  the equivalent narrow in-house Algorithm 1 implementation), and writes a
  byte-compatible **unencrypted** PDF (same objects, same xref, `/Encrypt`
  entry removed) to a private, randomly-named temp file - then calls the
  existing `SmalotPdfTextExtractor::extract()` against that temp file
  unchanged. **Recommended** - see section 11.
- **Option B - decrypt strings/streams inside a custom parser adapter**
  (intercept at the `Header`/`PDFObject` construction layer instead of
  producing a full second file). Avoids writing a temp file, but requires
  much deeper coupling to Smalot's internal object model and would need to
  be re-verified against every Smalot upstream release that touches that
  internal layer - a larger, more fragile integration surface for a smaller
  memory benefit (see section 9: Smalot's own parse overhead already
  dominates peak memory regardless of how the plaintext bytes are supplied
  to it).
- **Option C - fork/extend Smalot's parser security handling** (what
  `denysmedvid/pdfparser` actually did). Removes the temp-file step
  entirely, but means carrying a forked copy of `smalot/pdfparser` -
  divergent from every future upstream Smalot release (CVE fixes, parser
  correctness fixes), a genuine ongoing maintenance liability this project
  would own indefinitely, whether via `denysmedvid/pdfparser` directly (see
  its adoption risk in section 7) or a project-owned fork.
- **Option D - replace Smalot entirely for encrypted PDFs.** No pure-PHP
  library found in this or the V1.5.3 research does page-level text
  extraction *and* decryption together as one coherent library (the
  candidates in section 7 stop at decrypting bytes / producing a plaintext
  PDF, not at extracting structured page text) - this would still end up
  needing Smalot (or a full parser replacement, a much larger undertaking)
  for the actual text-extraction step, so it collapses back into Option A
  or C with extra work.

Compared on the task's criteria: Option A requires zero changes to Smalot
(no fork-maintenance burden, no drift risk against upstream), keeps 100% of
`DocumentExtractionService`/`ExtractMaintenanceDocumentJob`'s existing
contract and page-by-page persistence loop untouched (a new
`PdfTextExtractor` implementation is a drop-in, same as
`SmalotPdfTextExtractor` is today), is independently testable/characterizable
without touching Smalot at all, and isolates 100% of new crypto-sensitive
code behind one clear module boundary. Its implementation complexity is
concentrated in one well-scoped place (object-graph walk + rewrite, using a
vetted library for the actual cipher/key-derivation primitives rather than
hand-rolling them) rather than spread across a forked upstream dependency.

## 9. Large-File Memory Analysis

Measured directly against the real 121,833,361-byte document (PHP 8.2.33,
`memory_limit=1024M` to get past the point this milestone is measuring):

```
peak_memory_bytes = 491,700,224  (468.9 MB)
file_size_bytes   = 121,833,361
peak / file_size ratio = 4.04
```

This is the peak memory **just to reach the `/Encrypt` rejection point** -
`Parser::parseFile()` unconditionally does `file_get_contents()` (loads the
full 116MB into one PHP string) and `RawDataParser::parseData()` then
tokenizes the entire xref/object structure (42,236 objects, 100 object
streams) *before* `Parser::parseContent()`'s encryption guard ever runs.
Calling `SmalotPdfTextExtractor::extract()` directly against this file under
the *default* `memory_limit=128M` produces an **uncatchable PHP fatal**
("Allowed memory size ... exhausted") inside
`RawDataParser.php`, confirming empirically why
`DocumentExtractionService`'s V1.5.3 pre-flight `RESOURCE_LIMIT` guard
(`MEMORY_ESTIMATE_MULTIPLIER = 4`, checked against 50% of `memory_limit`
*before* ever calling the extractor) exists and is calibrated correctly -
the measured 4.04x ratio validates that constant almost exactly.

**Key finding**: Smalot's own parse overhead (~4x file size) is *inherent to
using Smalot at all* for the post-decryption text-extraction step, and is
completely independent of how a future decryption step supplies it with
plaintext bytes. This has a direct architectural consequence for section 8:

- A **decrypt-entirely-into-one-PHP-string** approach would need, at its
  peak, roughly (encrypted bytes, ~116MB, freed once decrypted) + (decrypted
  plaintext string, ~116MB) + (Smalot's own ~468MB parse overhead on that
  string) - and if the decryption step doesn't free the encrypted bytes
  before Smalot starts, all three coexist.
- A **decrypt-to-a-private-temp-file** approach (streaming: read a chunk of
  the input, decrypt it, write it to the temp file, repeat) bounds the
  *decryption step's own* memory to roughly the chunk size, not the file
  size - the encrypted-source and decrypted-temp-file bytes are never both
  fully resident in PHP memory at once. Smalot's subsequent `parseFile()`
  call against that temp file then incurs its own already-characterized
  ~468MB peak as a **separate, later, sequential phase** - the decryption
  step's memory is already released by the time Smalot's peak occurs, so
  the two costs do not stack.

Conclusion: the temp-file strategy is meaningfully better bounded for a
116MB-class document, not merely a stylistic preference - it removes one
entire ~116MB buffer from ever coexisting with Smalot's own peak, at the
cost of one temporary file on private disk (never Hostinger's `/tmp` public
path - see security requirements).

## 11. Security Requirements for a Future Implementation (V1.5.5)

Non-negotiable for whichever option is eventually implemented:

- No password logging, ever - not the empty string, not a future non-empty
  attempt, not in exception messages, not in `error_message`/audit fields.
- No encryption key (file key or per-object key) logging.
- No raw `/O`, `/U`, `/OE`, `/UE`, `/Perms` values in logs, exceptions, or
  API responses - fingerprint/length only, exactly as this document does.
- Any temporary decrypted artifact must live under the same private disk
  `DocumentStorageService` already uses (`storage/app/private/...`), never
  a publicly web-servable path, and never Hostinger's shared system `/tmp`.
- Random, unguessable temp filename (matching the existing
  `reset-opcache.php` deployment convention of "random name, use once,
  delete immediately").
- Restrictive file permissions on the temp artifact (owner-only, matching
  `shared/.env`'s existing `0600` convention).
- Guaranteed cleanup on success, on exception, on job failure, and on
  timeout where PHP allows it (register a shutdown function /
  `finally` block, not just a happy-path `unlink()`).
- The temporary decrypted artifact must never replace, rename, or modify
  the original uploaded PDF `DocumentStorageService` already manages -
  the original stays byte-identical and remains the sole system of record.
- Audit only high-level lifecycle metadata (e.g. "decryption attempted",
  "decryption succeeded/failed", classification code) - never raw
  cryptographic material, matching `GovernanceAudit::OMITTED_FIELDS`'s
  existing pattern for `error_message`/`raw_text`.
- Fail closed for any security-handler revision/configuration this project
  has not explicitly implemented and tested (R5/R6, split crypt filters,
  `/Identity` filters, RC4-only configurations if not implemented) - report
  `UNSUPPORTED_PDF_SECURITY` exactly as today, never attempt a best-effort
  partial decrypt.
- All cryptographic byte comparisons (`/U` authentication, any future MAC
  check) must use `hash_equals()` or equivalent constant-time comparison -
  never `===`/`strcmp()` on secret-derived material. (Already true of this
  milestone's `PdfSecurityInspector`.)
- Tests must include: correct rejection of a wrong/non-empty password
  (never accepted as if it were empty), and confirmation that no
  brute-force/dictionary-attempt code path exists anywhere in the
  implementation - the only credential ever tried is the empty string, by
  construction (no method parameter for a caller-supplied password), not by
  convention.

## 12. V1.5.5 Architecture Decision

**Selected approach: A - a vetted existing pure-PHP library, adapted behind
`PdfTextExtractor`, using the decrypt-to-private-temp-file strategy.**

**Why**: Section 7 found two credible, currently-maintained, pure-PHP,
Hostinger-compatible candidates that did not (or were not found to) exist at
V1.5.3's investigation time - most notably `tecnickcom/tc-lib-pdf-encrypt` +
`tc-lib-pdf-filter`, from the long-established TCPDF organization, with
active 2026-09 releases, CI, coverage tracking, and correct handling of
exactly the standard-handler R4/AESV2 profile this document characterizes.
Building the *authentication* half of Algorithm 2/5 in-house for
`PdfSecurityInspector` (this milestone) proved the algorithm is
well-specified and independently reproducible without error - but a full
*decryptor* additionally needs correct per-object AES/RC4 stream decryption,
crypt-filter table resolution, and PDF object-graph rewriting into a valid
plaintext document; adopting a maintained library for that larger surface
carries materially less ongoing security-maintenance burden than an
in-house implementation, provided the library is vetted and the integration
boundary stays narrow (Option A, section 8) - never depending on it, or any
library, for anything beyond decryption itself.

**Supported security profile**: PDF Standard Security Handler, `/V 4`, `/R
4`, `/CFM /AESV2` (AES-128-CBC), `/StmF` = `/StrF` (single, non-split crypt
filter), empty user password only. This exactly covers the real document
characterized in this milestone, and by extension the broad class of
Acrobat-produced "restrict editing, 128-bit AES, no open password"
documents this profile represents.

**Unsupported profiles** (fail closed, classified as
`UNSUPPORTED_PDF_SECURITY`, never a best-effort partial decrypt): Revisions
5/6 (AES-256, different SHA-256-based key derivation entirely - ISO
32000-2 Algorithm 2.A/2.B), any PDF requiring a real (non-empty) user
password (this project does not attempt password cracking, by design and by
policy), split `/StmF`/`/StrF` crypt filter configurations, `/Identity`
crypt filters, and public-key (certificate-based) security handlers.

**Memory strategy**: never hold the encrypted source bytes, the decrypted
plaintext, and Smalot's own ~4x-file-size parse structures all resident at
once (section 9). Keep `DocumentExtractionService`'s existing pre-flight
`RESOURCE_LIMIT` guard, and apply it to the *decrypted* file size estimate
(same as today, since decryption does not change the plaintext PDF's size
materially) before Smalot ever parses the temp file.

**Temp-file strategy**: stream-decrypt the input PDF (read a bounded chunk,
decrypt, write) directly to a new private, randomly-named file under
`storage/app/private/` (never a publicly servable path, never system
`/tmp`), matching `DocumentStorageService`'s existing private-disk-only
convention; hand that temp file's path to the existing, completely
