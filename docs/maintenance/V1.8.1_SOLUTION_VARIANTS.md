# V1.8.1 - Solution Variant Publishing

## 1. Problem

Read-only investigation of the real Production document (code C-1127, while preparing its
first-publish review) found the manual gives the **same error code two materially different
technician procedures** depending on which optional accessory hardware is installed
("PK-512/513" vs "PK-522"). A structural, read-only search confirmed this is a recurring pattern:
the heading shape `X.X.N C-DDDD (variant-label)` appears on 22 pages across at least 20 distinct
codes, and the accessory-model tokens themselves (`PK-512`, `PK-522`, `FS-531`, `FS-612`, `SD-510`,
`LS-505`, ...) each appear on dozens to over a hundred pages. Publishing such a code with only one
technician procedure would silently drop the other variant.

## 2. Architecture decision

**Additive extension of `maintenance_error_solutions`** - one nullable column,
`applicability_label VARCHAR(160) NULL`. No new table, no destructive change.
`maintenance_error_solutions` was already a multi-row, ordered table (unique on
`machine_error_code_id` + `step_number`; any number of rows can already belong to one code); it
only lacked a way to say **which** hardware/accessory/model context a row applies to.
`step_number` keeps its existing meaning - an ordered solution-**entry** index, not a literal
step-in-procedure counter (each row already holds one complete narrative). `NULL` means "generally
applicable", exactly the pre-existing unlabelled behavior every prior publish path already produces.

A dedicated variant table was rejected as over-modeling: it would require joining across a new
relation for something the existing table already stores as rows.

## 3. Solution variant identity

A proposed `(applicability_label, instruction)` pair is compared against a code's **existing**
solution rows sharing the same normalized label:

| Existing rows with that label | Match found (squashed instruction) | Classification |
|---|---|---|
| none | - | `NEW_VARIANT` |
| >= 1 | yes | `IDENTICAL` (skipped, no duplicate) |
| >= 1 | no | `CONFLICT` (refused, never silently resolved) |

Same instruction under a **different** label is a different, legitimate variant. The same label
with **materially different** instruction (including two unlabelled/`NULL` solutions with
different text - Section 6 of the spec explicitly required this) is a `CONFLICT`, never a silent
second anonymous row.

## 4. Publish semantics (`KnowledgeGroupPublisher`)

The request now carries `technician_solutions: [{applicability_label, instruction}, ...]`
(0..N items) alongside the unchanged shared canonical fields (title/description/operator
guidance). **Backward compatible**: the pre-V1.8.1 single `technician_solution` string is still
accepted and internally wrapped as one unlabelled proposal; if both are sent, the array wins.

**Group outcome** (`plan()['group_outcome']`): `CREATE` | `UPDATE_SHARED` | `ADD_VARIANTS` |
`NO_CHANGE` | `CONFLICT`. A solution `CONFLICT` fails the **whole** publish - never a partial
publish of only the non-conflicting variants. `UPDATE_SHARED` takes priority in the label even
when a variant is also proposed in the same request (both are still applied together once
confirmed - Section 7's "planned and applied independently, then combined safely").

**Canonical occurrence is immutable once a group is published** (V1.8.1 addition): the first
publish fixes which occurrence anchors the group; a later request naming a different occurrence is
refused (`CANONICAL_MISMATCH`) rather than silently re-anchoring.

**A published group's shared fields can now be updated later** (architecture change from plain
V1.8, where any post-publish difference was a flat, permanent 409): a shared-field difference goes
through the *same* `confirm_update` gate an `EXISTING`/`POTENTIAL_UPDATE` collision already used
pre-publish. `confirm_update` only ever gates shared-field changes; it never overrides a solution
`CONFLICT`, which always needs a fresh review.

**Idempotency before staleness**, extended to the full proposal: a retry of an already-completed,
byte-identical publication (shared fields **and** every solution variant **and** every reference)
succeeds without writing, even with an expired token. A request that only *adds* a new labelled
variant, or updates shared fields with explicit confirmation, is a legitimate mutation of an
already-published group.

**Step numbers**: consecutive, starting at `max(step_number) + 1`, assigned only to `NEW_VARIANT`
proposals in submission order; `IDENTICAL` proposals consume no sequence number. Safe under
concurrent publish attempts for the same code via the existing `lockForUpdate()` row lock (a
brand-new code's create-race is still guarded by the pre-existing `(account, model, code)` unique
index, unchanged from V1.8).

**Staleness fingerprint** now folds in every existing solution row's `(label, instruction)` pair
(not just a count/max-step), so an out-of-band edit to existing solution text also invalidates a
stale preview.

## 5. Audit

`maintenance_knowledge_group.published` gains `solutions_proposed`, `solutions_added`,
`solutions_skipped_identical`, and a bounded (300-char), comma-joined `applicability_labels` list
of the labels actually added. Four new allowlist entries in `GovernanceAudit::FIELDS`. Instruction
text stays covered by the existing `OMITTED_FIELDS` (`instruction`, `technician_solution`) -
never logged. `publish_mode` gains a fourth value, `variants_added`, distinct from
`created`/`updated`/`unchanged`.

## 6. API

`POST code-groups/{code}/publish-preview` and `/publish` both accept `technician_solutions[]`
(each `{applicability_label, instruction}`) alongside the legacy `technician_solution` string.
The preview response's `solutions[]` array reports each proposed variant's `applicability_label`
and `status` (`NEW_VARIANT`/`IDENTICAL`/`CONFLICT`), with the existing instruction echoed back only
for a `CONFLICT` (so the reviewer can compare). `proposed.solutions` echoes back exactly what was
submitted (matching the existing title/description/operator_guidance echo pattern) so the frontend
can detect a stale on-screen preview by simple equality. No hashes are exposed. Authorization
(`canManageCatalogScope`) and tenant isolation are unchanged.

## 7. Frontend

The single technician-solution textarea became a small repeatable list (`SolutionEditor`): each
row has an optional "Applicability" input (generic placeholder `"e.g. Accessory A/B"` - real
labels are reviewer-authored data, never hard-coded in product code) and an instruction textarea,
with Add/Remove controls. The publish preview groups solutions and shows each one's status
(`New variant` / `Already exists` / `Conflict`); a `CONFLICT` disables normal confirmation via the
existing `can_publish`/`blocked_reason` gate - no separate override control exists. The published
Error Codes list (`ErrorCodeKnowledgeSection`) groups steps by `applicability_label` (in
step_number order, never re-sorted), showing `[General]` only when more than one group exists.

## 8. Not in this milestone

Updating an already-published *shared field* without the group having first been published (that
pre-publish collision path is untouched); a way to *remove* or edit an already-published solution
variant; any accessory/compatibility-matrix modeling beyond the free-text label; any deployment
or real publication of C-1127.

## 9. C-1127 status

Untouched throughout this milestone (verified read-only before, during and after implementation):
pages 32/949 remain `REJECTED` (from V1.8's human-review triage), pages 1348/1460/1461/1730 remain
`DRAFT`, the catalog remains empty for C-1127, and no `maintenance_knowledge_group.published` audit
event exists. C-1127's real publication - now correctly representable as one canonical code with
two labelled technician-solution variants - is a separate, human-approved next step.
