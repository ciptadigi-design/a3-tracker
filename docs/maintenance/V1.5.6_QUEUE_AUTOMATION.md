# V1.5.6 - Queue Automation & Reliability

Closes the operational gap left after V1.5.5/V1.5.5.1: the real Konica
extraction completed successfully in Production, but only because an
operator manually ran `queue:work` over SSH. This milestone makes queue
processing automatic via Hostinger cron, with no SSH/Artisan step required
for normal product use, and corrects two timing defects the earlier manual
run happened not to trigger.

## 1. Timing defects found and fixed

Auditing `RunQueueOnce` (`a3:run-queue`) against the real ~107-second Konica
extraction (V1.5.5 Production acceptance) found two values only ever
validated against fast synthetic-fixture jobs:

- **`--timeout` was never passed to `queue:work`**, silently defaulting to
  its own CLI default of 60 seconds. The real 107s job still completed
  successfully despite that default, even with both `pcntl` and `posix`
  loaded on Production - proving the alarm-based per-job kill did not fire
  in that run, for a reason not fully root-caused. Relying on that
  non-enforcement was never safe to depend on. Fixed: explicit
  `--timeout=300` (~2.8x margin over the observed real job).
- **`retry_after` (config/queue.php, `DB_QUEUE_RETRY_AFTER`) defaulted to
  90 seconds** - below the observed ~107s job. Unlike `--timeout`, this is
  enforced unconditionally by the database queue driver's own
  `reserved_at < now() - retry_after` query on every pop, regardless of
  pcntl/signals. A legitimately-still-running job past its `retry_after`
  becomes poppable by a second worker mid-extraction - the actual
  overlapping-workers correctness risk automatic (frequent) cron execution
  would have exposed sooner or later. Fixed: raised to 420s (120s margin
  above the new 300s `--timeout` ceiling).

The overlap-protection `Cache::lock('a3-queue-runner', ...)` TTL was
previously a fixed `--max-time + 60s` (110s with defaults) - only 3 seconds
above the real 107s job it needed to survive. It is now derived from the
same values actually passed to `queue:work`: `max-time + timeout + 30s`
(380s with defaults), so it cannot expire while a legitimately slow job (up
to the full `--timeout` ceiling) is still running.

## 2. Observability

`a3:run-queue` previously either printed one terse line or nothing
meaningful on the common paths. It now always prints an explicit,
machine-readable `QUEUE_RUNNER_STATUS=...` outcome (`STARTED`, then one of
`SKIPPED`/`COMPLETED`/`FAILED`, plus `REASON`, `EXIT_CODE`,
`JOBS_PROCESSED`, `JOBS_FAILED`, `JOBS_TIMED_OUT`) - a cron tick's outcome is
never something an operator has to infer from silence. See
`docs/hostinger/HOSTINGER_QUEUE_SETUP.md` for the full contract and
troubleshooting guide.

## 3. Cache lock backend finding

Existing documentation claimed `CACHE_STORE=database` was already
Production's configuration. Read-only verification during this milestone
found Production's `shared/.env` actually carries an explicit
`CACHE_STORE=file` override - `cache.default` resolves to `file`
(`storage/framework/cache/data`), not the `cache_locks` database table. This
is still safe and correct for this single-host, one-active-release
architecture (see `docs/hostinger/HOSTINGER_QUEUE_SETUP.md` for the full
reasoning) - no `CACHE_STORE` change was made; only the documentation was
corrected. Changing the account-wide cache driver would have been unrelated
scope creep for this milestone.

## 4. Small controlled acceptance mechanism

`QueueHealthCheckJob` + `a3:queue-health-check` (dispatch/check) is a
deliberately tiny, side-effect-free job/command pair - no business
mutation, no public HTTP route, writes only a timestamp under a
caller-supplied token - built specifically so cron automation could be
proven end to end without re-running the real 2639-page Konica extraction
just to exercise cron plumbing.

## 5. Production deployment

Deployed via the standard `docs/production/RELEASE_PROCEDURE.md` gates:
`production-backup.sh` → `BACKUP_GATE=PASS` (DB + frontend both `VALID`,
`db_required_tables_ok=true`), fresh `git clone` + checkout of the exact
CI-green candidate SHA (never the dirty local worktree), `composer install
--no-dev --classmap-authoritative`, shared `.env`/storage linking, release
identity + config cache, `verify-release.sh` → `RELEASE_PREFLIGHT=PASS`,
atomic `current` symlink swap, one-shot web-SAPI OPcache reset, full smoke
suite. No migration (schema remained batch 15). `public_html` inode and
`.htaccess` hash unchanged throughout. The pre-existing real Konica
extraction (`035c1406-2f57-475d-8b60-7ddc98d0a172`, COMPLETED, 2639 pages)
and its source PDF (unchanged size/SHA256) were verified untouched
throughout.

## 6. Cron acceptance (the actual proof)

Hostinger's SSH shell has no `crontab` access at all (confirmed: `crontab`
absent from `$PATH`, `/var/spool/cron/crontabs/` inaccessible) - the cron
entry had to be installed by the operator through hPanel's own UI
(Advanced → Cron Jobs → "Daftar Cron Job"), which this environment cannot
do programmatically.

Installed entry:

```
Schedule: */5 * * * *
Command:  /usr/bin/php /home/u777904340/a3-production-app/current/backend/artisan a3:run-queue
```

**Acceptance procedure:** with the queue confirmed empty, a single
`QueueHealthCheckJob` was dispatched via `a3:queue-health-check --dispatch`
(02:39:02 UTC). The worker was deliberately never invoked manually. The job
sat genuinely unconsumed for over 34 minutes before the cron entry existed
(a full first investigation cycle, independently confirmed via the
`storage/framework/cache/data` lock directory's mtime staying pinned at the
release's own creation time - direct proof `a3:run-queue` had not executed
even once). After the operator installed the `*/5` entry above, the very
first scheduled boundary (03:25:00 UTC) automatically:

- touched the lock directory for the first time since deployment
  (mtime 03:25:01 UTC, matching the boundary + ~1s dispatch latency),
- drained the pending job (`jobs` table: 1 → 0), and
- completed it (health-check marker `completed_at=2026-09-19T03:25:01+00:00`,
  matching exactly).

No manual `queue:work`/`a3:run-queue` invocation occurred at any point
during this acceptance. `failed_jobs` remained exactly the 2 pre-existing
V1.5.3 historical entries throughout - no new failure, no duplicate, no
retry storm. The cron command targets `current/backend/artisan` (a symlink
path, not a release-specific SHA), so a future atomic release swap moves
cron execution to the new release automatically, with no cron
reconfiguration required - this was exercised directly, since the command
that fired was written against `current` before this exact release existed
and still resolved correctly against it.

## 7. Baseline product flow going forward

Upload PDF → click Extract Knowledge → API creates the extraction and
dispatches `ExtractMaintenanceDocumentJob` onto the same `database`/
`default` queue this milestone proved `a3:run-queue` drains automatically →
UI shows `PENDING` → within at most 5 minutes (the installed cron cadence),
`a3:run-queue` fires, acquires the lock, and processes it → `PROCESSING` →
`COMPLETED` → existing polling/UI surfaces the result. No SSH, no manual
Artisan command, no operator intervention. The V1.5.x manual
calibration/acceptance procedures (memory guard calibration, real-document
compatibility validation) were development-time validation steps for this
one milestone chain, not part of the ongoing product workflow.
