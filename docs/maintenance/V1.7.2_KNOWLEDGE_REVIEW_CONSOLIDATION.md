# V1.7.2 - Knowledge Review Consolidation

## 1. Problem

V1.7.1 calibrated the real Production V2 import: 2680 candidate rows, 705 distinct
normalized codes (about 3.8 rows per code). Detector output is structurally sound; the
problem is review ergonomics. A reviewer works on a *code*, but the workflow showed 2680
independent rows, and clearing the 1,187 table-of-contents / index rows would have taken
twelve 100-ID batches selected by hand.

V1.7.2 turns review into a consolidated, code-centred experience while preserving every
underlying candidate row and its provenance. No detector change, no new persisted state,
no AI, no automatic approval, no automatic publishing.

## 2. Data model

**No migration. No new table. No new column.** `maintenance_knowledge_entries` stays the only
source of truth. A *code group* is a projection (a server-side `GROUP BY normalized_code`
inside one import) recomputed on every request, so it cannot drift from its rows.

### Group review state (derived, first matching rule wins)

`published` means `status = APPROVED AND published_at IS NOT NULL` (there is no separate
PUBLISHED status in this domain).

| State | Rule |
|---|---|
| `PUBLISHED` | at least one occurrence is published |
| `APPROVED` | none published, at least one occurrence APPROVED |
| `UNREVIEWED` | every occurrence is DRAFT |
| `REJECTED` | every occurrence is REJECTED |
| `PARTIALLY_REVIEWED` | anything else (a mix of DRAFT and REJECTED) |

`best_evidence` is the strongest evidence among the group's rows (HIGH > MEDIUM > LOW). It is
detector evidence, never ground truth. `candidate_status_counts` splits APPROVED (not yet
published) from PUBLISHED so the four counts always sum to `occurrence_count`.

## 3. Endpoints (all under `/api/v1/maintenance/document-imports/{id}`)

| Endpoint | Access | Purpose |
|---|---|---|
| `GET code-groups` | member of the owning account (same rule as `entries`) | paginated groups + import-level `summary` |
| `GET code-groups/{code}` | same | one code, every occurrence, individually |
| `POST entries/bulk-review/preview` | `canManageCatalogScope` | read-only preview of a filter-based reject/restore |
| `POST entries/bulk-review/apply` | `canManageCatalogScope` | apply exactly the previewed set |
| `POST entries/bulk-review` | unchanged (V1.7) | explicit-ID bulk, 100-ID cap |

Pagination is mandatory: `per_page` in 10 / 25 / 50, default 25. Sorts: best evidence
(default), occurrences, first page, code, with deterministic tie-breaks. The list never
returns candidate text. The detail returns each row's stored, already-bounded `description`
excerpt (the same text the candidate row holds) and never page text.

## 4. Filters

One definition (`KnowledgeCandidateFilter`) feeds the list, the detail and the bulk flow.

- **Row-level** (a property of one candidate): `code`, `evidence`, `collision_status`,
  `status` (read views only), `source_page_from/to`, `reference_like`. Criteria are ANDed on
  the **same row**: "HIGH within pages 1-50" never matches a code whose HIGH row is on page
  100 just because another row of it is on page 10.
- **Group-level** (read views only): `review_state`, `min/max_occurrences`, and
  `best_evidence` (HIGH / MEDIUM / LOW / `STRONG` = HIGH or MEDIUM).
- A group's own counts always cover **all** its rows; `matching_occurrence_count` reports how
  many satisfy the active row-level criteria.
- `reference_like` re-reads the detector's own stored signal: the detector already ranks a
  match LOW when its stored context contains 5+ dots (a dotted leader). It is a `LIKE`
  over the existing `description`; nothing new is stored and the text is never returned.
- Page overlap: a candidate covering `[start, end]` matches a window when the ranges overlap.
- No real-manual page ranges appear anywhere in product code.

## 5. Filter-based bulk triage

Two steps, server-driven, REJECT and RESTORE only (no approve, no publish, no delete):

1. **Preview** - returns `matching_count`, `eligible_count`, `excluded_count` (with a
   breakdown), a deterministic, bounded (10) structural sample, and a signed confirmation
   token. Mutates nothing.
2. **Apply** - re-derives the eligible set **inside a transaction with row locks** and
   proceeds only if it is exactly the previewed set.

Eligibility: reject = `DRAFT` and `published_at IS NULL`; restore = `REJECTED` and
`published_at IS NULL`. A published or APPROVED row is never eligible. Everything is scoped
to exactly one import.

**Stale / tamper protection** - the token is stateless (no table): an HMAC-SHA256 over
`{import, action, hash of canonical filters, acting user, eligible count, digest of the
sorted eligible IDs, expiry}` keyed from `APP_KEY`.

| Situation | Result |
|---|---|
| a candidate reviewed / added / published after the preview | 409 (eligible set differs) |
| token older than 15 minutes | 409 |
| filters, action, import or user differ from the preview; forged or malformed token | 422 |
| client-sent `affected` / `affected_count` | ignored; the server reports what it changed |
| no narrowing filter, unknown filter key, `status` / `review_state` in a bulk body | 422 |
| more than 5,000 eligible | preview blocks (`TOO_MANY_CANDIDATES`), no token issued |

## 6. Audit

`knowledge_candidates_filter_bulk_rejected` / `knowledge_candidates_filter_bulk_restored`,
target = the import. Metadata is `affected_count`, a 16-char `filter_fingerprint`, and a
bounded (<=200 chars) `filter_summary` built from validated enum/integer/code values. Two
allowlist entries were added to `GovernanceAudit::FIELDS`; `description` stays omitted. No
candidate text, no ID list, no path is ever logged (asserted by tests).

## 7. Frontend

PDF-derived imports open on **Code groups**; **All candidates** (the unchanged flat list
and the V1.7 ID-based selection) is one tab away. The group list shows code, best-evidence
badge, occurrences, evidence mix (H/M/L), page range, derived review state, collision and
reference-like signals. Summary cards and the progress line are backend aggregates.
Presets ("Strong evidence", "Low-only", "Reference-like", "Not yet reviewed") are ordinary,
visible filters. "Evidence is detector evidence, not verification" is stated in the UI.

Triage opens a modal `alertdialog` that auto-previews (read-only), shows the counts and
sample, requires an explicit confirm button, adds an acknowledgement checkbox above 100
eligible candidates, reports the server's affected count, and on a stale/invalid
confirmation says nothing changed and offers "Preview again". Restore uses the same flow.
The dialog freezes the filters it opened with. Manager-only controls render only for
managers. Narrow-screen CSS collapses rows to one column.

## 8. Performance

One grouped aggregate per page, plus at most two small lookups scoped to that page's codes
(page provenance without text; matching counts when row filters are active) and two
summary queries. **5 queries unfiltered / 6 filtered, independent of how many groups are
listed** (asserted by a test that compares 5 vs 45 groups). No N+1, no PHP-side grouping,
no `GROUP_CONCAT`. Only portable SQL (`CASE`/`SUM`/`COUNT`/`LIKE`).

## 9. Real-data read-only validation (Production, MariaDB 11.8, aggregates only)

The exact SQL the read model issues was run read-only against the real V2 import:

- 705 groups from 2680 candidates, 0 ungrouped.
- Best evidence: HIGH 534 / MEDIUM 19 / LOW-only 152 codes; all UNREVIEWED.
- Filters reproduce the calibrated clusters with no page knowledge in the product:
  LOW within a 9-page window = 540, LOW within a 12-page window = 647,
  LOW + reference-like = 557 (all eligible).
- LOW rows of LOW-only codes = 153; no LOW-only code sits in the dotted-leader cluster, so
  the TOC rows belong to codes that also have HIGH/MEDIUM body occurrences - which is why
  triage acts on rows, not on a group as a whole.

Nothing was written.
