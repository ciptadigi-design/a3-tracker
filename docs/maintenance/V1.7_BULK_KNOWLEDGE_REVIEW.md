# V1.7 - Bulk Knowledge Review & Triage

## 1. Operational problem

V1.6/V1.6.1 Production acceptance proved the deterministic candidate
pipeline works end to end: the real 2639-page Konica document produced
**2680** draft candidates in one import (HIGH 624 / MEDIUM 578 / LOW 1478),
all correctly provenance-tracked, zero fabrication, zero publication. That
success created a new problem: reviewing 2680 candidates one at a time
through the existing individual approve/reject/publish workflow is not
practical. This milestone adds a bounded, transactional bulk-triage layer
on top of the existing review workflow - it does not replace it.

## 2. Review-state semantics (audited, not reinvented)

`maintenance_knowledge_entries.status` is `DRAFT` / `APPROVED` / `REJECTED`
(V1.3, unchanged). Critically, **there is no separate `PUBLISHED` status
value** - `MaintenanceKnowledgePublishService::publish()` only ever sets
`published_at`, leaving `status` at `APPROVED`. "Published" in this domain
is `status=APPROVED AND published_at IS NOT NULL`.

This is why bulk review is scoped to exactly two transitions, kept in their
own `BULK_TRANSITIONS` map (deliberately separate from the existing
single-entry `ENTRY_TRANSITIONS`, not merged into it):

```
reject:  DRAFT    -> REJECTED
restore: REJECTED -> DRAFT
```

Bulk review **never reads or writes an `APPROVED` row**. This makes it
structurally impossible - not just runtime-checked - for a bulk action to
ever reach a published row, since published rows are always `APPROVED`.
The `published_at IS NULL` check inside the transaction is defense-in-depth
on top of that structural guarantee, not the only thing preventing it.

Bulk approve and bulk publish are explicitly out of scope, per the
mission's own default: evidence is a review signal, not a truth label -
HIGH does not mean publishable, LOW does not mean incorrect. A human still
makes every approve/publish decision individually, exactly as before.

## 3. Selection model

Page-level only (Section D's explicitly-endorsed simpler option) - no
cross-page "select all 1,478 matching candidates" in V1.7. A checkbox
renders only for `DRAFT`/`REJECTED` rows (never `APPROVED`, so a published
row can never even be selected). Selection is cleared whenever the review
status, collision status, or evidence filter, the code search, or the
current page changes - implemented as React's documented "adjust state
during render" pattern (a derived value compared against its own previous
value), not `useEffect` + `setState` (which the project's lint config flags
as an avoidable extra render for state that is fully derivable from props).
A selection can never silently refer to rows the reviewer can no longer see.

## 4. API contract

```
POST /maintenance/document-imports/{import}/entries/bulk-review
{ "entry_ids": ["...", "..."], "action": "reject" | "restore" }

-> { "data": { "action": "reject", "affected": 25 } }
```

- Authorization: the exact existing `AccountAccessResolver::canManageCatalogScope()`
  path, no new capability.
- Batch limit: **100** entries/request (`BULK_BATCH_LIMIT`) - the existing
  candidate-list page size is 50, so 100 is a documented 2x margin, never an
  unbounded array.
- `entry_ids`: required, 1-100 UUIDs, deduplicated server-side (submitting
  the same ID twice is safe, never double-counted).
- `action`: required, exactly one of `reject`/`restore`.

## 5. Atomicity and fail-closed validation

Runs inside one `DB::transaction()`:

1. Lock (`lockForUpdate()`) and fetch every row matching `import_id` +
   the submitted `entry_ids`.
2. If the fetched count doesn't match the submitted (deduplicated) ID
   count, at least one ID belongs to a different import (or doesn't exist)
   - **the entire request fails, zero mutation**, `409 Conflict`.
3. If any fetched row's current `status` isn't the transition's expected
   source status, or its `published_at` isn't null, **the entire request
   fails, zero mutation**, `409 Conflict` - this is also how stale
   concurrent state is handled (Section K): if another reviewer already
   acted on one selected entry between page load and submit, the whole
   batch is rejected rather than silently mutating only the
   still-eligible rows.
4. Only if every row passes both checks: one set-based `UPDATE ... WHERE
   import_id = ? AND id IN (...)`, then one audit record, then commit.

No partial success is possible. The response's `affected` count always
equals the number of rows actually transitioned.

## 6. Performance

Set-based throughout: one locked `SELECT`, one `UPDATE`, one audit
`INSERT` per request, regardless of batch size (1-100) - never N
independent queries. No queue involved; bulk review is synchronous
(bounded by the 100-row limit, this is fast enough not to need one).

## 7. Audit

`knowledge_candidates_bulk_rejected` / `knowledge_candidates_bulk_restored`,
targeting the import (not each entry individually - one record per bulk
action). Metadata carries only `affected_count` (added to
`GovernanceAudit::FIELDS` for this milestone) - never raw candidate text,
descriptions, or an unbounded entry-ID list. Verified by test that the
audit payload never contains fixture "manual" prose.

## 8. No deletion

Rejecting never deletes a row. `normalized_code`, `source_page_start`/
`source_page_end`, `evidence`, `collision_status`, `description`, and
`created_at` all survive a bulk reject unchanged - only `status` moves to
`REJECTED`. This is why `restore` (REJECTED -> DRAFT) exists: a LOW-evidence
candidate rejected today may turn out to matter later, and nothing about it
was ever destroyed.

`candidate_count` and `evidence_summary` on the import are **not** reduced
by rejection - they count every candidate the detector produced, regardless
of current review status, matching the existing V1.6.1 semantics exactly
(verified by test).

## 9. Tenant isolation

Every check is scoped through the import's own `document.account_id` via
the existing authorization path - a foreign account's import returns `403`
before any entry is even queried. Cross-import requests (some entry_ids
belonging to a different import) fail closed per Section 5 above, verified
even for a request mixing genuinely-eligible IDs from the caller's own
import with foreign IDs - the eligible ones are not silently processed.

## 10. Frontend

Extends the existing `KnowledgeImportDetail` review dialog rather than a
new module: a checkbox column, a "select all on this page" row, a compact
inline bulk-action bar that appears only once something is selected, and a
confirmation dialog (`BulkReviewDialog`, reusing `BlockingDialog` -
`role="alertdialog"`, matching the existing `RetireMachineDialog`
convention - never a browser `confirm()`). The offered action is derived
from the selection's shared status: a uniform `DRAFT` selection offers
"Reject selected"; a uniform `REJECTED` selection offers "Restore to
draft"; a mixed selection offers neither, rather than guessing intent.
Evidence/status/collision filters and code search are unchanged; individual
approve/reject/publish/edit actions remain fully available alongside bulk
triage.

## 11. No migration

`status` already supports both transitions (`DRAFT`/`REJECTED` already
existed as values). No new columns were added for selection, batching, or
bulk metadata - `GovernanceAudit::FIELDS` gained one new allowlisted key
(`affected_count`), which is metadata-shape, not a schema change.

## 12. Production acceptance plan (not performed in this milestone)

This is an implementation-only milestone - Production was not touched, and
the real 2680-candidate import (`4b2c1351-...`) was not mutated. The
smallest defensible next step: deploy via the established release
procedure, then perform one small, deliberately reversible real
acceptance - select a handful of genuinely LOW-evidence candidates from a
known dense index/glossary page range (e.g. pages 30-38), bulk-reject them,
verify `affected` matches the selection size, verify `machine_error_codes`/
`maintenance_error_solutions`/`maintenance_document_references` remain
unchanged, then bulk-restore the same candidates back to `DRAFT` to prove
the operation is genuinely non-destructive on real data before it is used
at real scale (all 1478 real LOW candidates).
