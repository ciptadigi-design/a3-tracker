# V1.5.5 - AESV2 Secured PDF Extraction

Implements real extraction support for exactly the security profile V1.5.4
characterized against the real production document. No deployment, no
Production mutation, no `.env` change, no migration - this is a pure
application-code change on `develop`.

## 1. Supported Security Profile

The Standard Security Handler configuration proven against the real
production Konica document in V1.5.4, and nothing broader:

| Field | Required value |
|---|---|
| `encrypted` | `true` |
| `/Filter` | `/Standard` |
| `/V` | `4` |
| `/R` | `4` |
| Key length | 128 bits |
| Stream cipher | `/AESV2` (AES-128-CBC) |
| String cipher | `/AESV2` |
| Empty user password | confirmed valid (Algorithm 5 authentication succeeds) |

`PdfSecurityProfile::isSupportedAesV2Profile()` is the single, exhaustive
capability predicate - every field above must match exactly; there is no
"unless" clause and no partial match.

## 2. Explicit Unsupported Profiles

Every one of these still ends in `UNSUPPORTED_PDF_SECURITY`, identical to
V1.5.3/V1.5.4 behavior - this milestone changes behavior for exactly the one
profile above and nothing else:

- Revisions 2, 3, 5, 6 (RC4-40, RC4-128, and both AES-256 revisions - R5/R6
  use a completely different, SHA-256-based key derivation, ISO 32000-2
  Algorithm 2.A/2.B, not implemented here).
- RC4 as the stream/string cipher at any revision, even if `--allow-weak-crypto`-
  style tooling could produce a "valid" file - out of scope by design, not
  merely unimplemented (RC4 is cryptographically broken; see
  `tc-lib-pdf-encrypt`'s own README security notice, quoted in section 3).
- A real (non-empty) user password. **Never attempted, at any point, for any
  document.** There is no method parameter, config option, or code path
  anywhere in this codebase through which a password other than the empty
  string could be supplied - see section 9.
- Split crypt filters (`/StmF` != `/StrF`), `/Identity` crypt filters, and
  public-key (certificate-based) security handlers.
- Any document where `/ID` is missing (Algorithm 2 requires it) or the
  `/Encrypt` dictionary is malformed.

## 3. Dependency Decision

**Added:** `tecnickcom/tc-lib-pdf-encrypt` `^2.11` (2.11.2 installed) -
one package, zero new transitive dependencies (`composer.lock` diff:
`tecnickcom/tc-lib-pdf-encrypt` only).

**Not added:** `tecnickcom/tc-lib-pdf-filter`. Its role (decoding
compression/crypt-filter chains) is already covered, for the one filter this
profile actually needs (`FlateDecode`), by `Smalot\PdfParser\RawData\FilterHelper`
- already an installed, in-use dependency of `smalot/pdfparser` - reusing it
keeps decoding behavior byte-identical to what Smalot already does for every
unencrypted PDF, and avoids the "do not add both automatically if one is
sufficient" trap.

**Not adopted:** `denysmedvid/pdfparser` (the fork identified in V1.5.4) -
its `StandardSecurityHandlerR4` implementation is spec-correct on inspection,
but it is a 1-star, single-contributor fork with no community audit trail
for security-sensitive code; `tc-lib-pdf-encrypt` comes from the established
TCPDF organization with active 2026-09 releases, CI, and coverage tracking.

**Verification performed (Packagist + installed package, not just Packagist
metadata):**

```
composer show tecnickcom/tc-lib-pdf-encrypt

  license  : LGPL-3.0-or-later
```

No binary, no `ext-ffi`, no shell execution, no native library - pure PHP,

## 4. Capability-Gate Evidence

Per the task's explicit gate ("PROVE the relevant API with a tiny isolated
experiment... IF the libraries provide sufficient, maintained functionality
... without recreating a large PDF parser/rewrite engine: proceed"):

An isolated experiment (separate scratch Composer project, removed before
committing anything) called `Com\Tecnick\Pdf\Encrypt\Decrypt::authenticate('')`
and `decryptString()` directly against the real production document's actual
`/Encrypt` dictionary values (read via `RawDataParser`, never committed) and
compared the result against this codebase's own from-scratch implementation
(`PdfSecurityInspector`'s Algorithm 2/5, already shipped in V1.5.4):

```
tc-lib authenticate("") result: true
tc-lib authenticated role: user
tc-lib decryptString() -> gzuncompress() -> 2863 bytes, matching this
  codebase's own independent AES-128-CBC + gzuncompress computation byte
  for byte, on the real document's actual object-stream ciphertext.
```

Both approaches independently agreed. **The gate passed**: `tc-lib-pdf-encrypt`
provides sufficient, correct, maintained key-derivation and per-object
decryption primitives. What it does **not** provide - and what no evaluated
library provides - is PDF object-graph traversal or serialization; that
remained this project's own, much smaller, responsibility (section 5),
critically **not** requiring a new PDF parser (Smalot's own already-battle-
tested `RawDataParser` is reused unmodified) or a PDF writer/serializer at
all (see section 5 for why).

Custom crypto required beyond the library: none for content decryption. This
project's own from-scratch Algorithm 2/5 (`PdfSecurityInspector`, shipped in
V1.5.4) remains in place as the classification/authentication-check layer;
`tc-lib-pdf-encrypt`'s `Decrypt` class is the one used for actual per-object
key derivation and AES-128-CBC decryption once V1.5.5 commits to the secured
path.

## 5. Architecture

```
ProfileAwarePdfTextExtractor  (bound as PdfTextExtractor in AppServiceProvider)
  |
  +-- try SmalotPdfTextExtractor::extract()   (unchanged since V1.5.3)
  |     |
  |     +-- succeeds -> return                (unencrypted PDFs: zero extra cost)
  |     +-- throws UNSUPPORTED_PDF_SECURITY -> continue below
  |     +-- throws anything else -> re-throw unchanged
  |
  +-- PdfSecurityInspector::inspect()          (unchanged since V1.5.4)
  |     +-- not the supported profile -> throw UNSUPPORTED_PDF_SECURITY
  |
  +-- SecuredPdfTextExtractor::extract()       (new)
        +-- RawDataParser::parseData()          (Smalot's own, unmodified)
        +-- AesV2StandardSecurityHandler         (new - wraps tc-lib-pdf-encrypt)
        |     re-authenticates independently (fail-closed even if ever called directly)
        +-- SecuredObjectDecryptor::decryptAll()  (new)
        |     decrypts every string/stream token IN MEMORY, using
        |     PdfObjectDictionaryReader (shared with PdfSecurityInspector,
        |     extracted from it this milestone with zero behavior change -
        |     verified by re-running its existing V1.5.4 tests unmodified)
        +-- SecuredParserBridge::buildDocument()  (new - Parser subclass)
              reuses Smalot\PdfParser\Parser's own PROTECTED parseObject()/
              parseTrailer() and its existing /Type /ObjStm expansion logic -
              exactly the code path that already turns 28,195 of the real
              document's 42,236 objects (the ones compressed inside 100
              /ObjStm containers) into a flat object graph for an
              UNENCRYPTED file. Once SecuredObjectDecryptor has decrypted an
              /ObjStm container's own stream content, this existing Smalot
              code expands it exactly as it always has - completely
              unmodified, not even aware anything was ever encrypted.
```

**Why no PDF rewrite/serializer was needed** (this is the key discovery that
changed the architecture from what V1.5.4 anticipated): `Smalot\PdfParser\
Parser::parseContent()` calls `RawDataParser::parseData()` to get an
already-fully-tokenized `$data` map, THEN (only afterward) checks for
`/Encrypt` and throws. Its object-construction methods (`parseObject()`,
`parseTrailer()`) operate entirely on that in-memory `$data` structure - they
never re-read the file. This means decryption only has to mutate the
in-memory token map (replacing each string/stream token's ciphertext with
plaintext) before handing it to those same methods via a subclass -
`SecuredParserBridge extends \Smalot\PdfParser\Parser`, calling its own
parent's `protected` methods. **No vendor file is modified, forked, or
patched** - the installed `smalot/pdfparser` package is byte-for-byte what
Composer installed; `git diff` on `vendor/` is empty. This is why V1.5.5
never needed the decrypt-to-temp-file rewrite V1.5.4's Option A assumed
would be necessary.

**DocumentExtractionService / ExtractMaintenanceDocumentJob changes: none.**
Only `AppServiceProvider`'s `PdfTextExtractor` binding changed (from
`SmalotPdfTextExtractor::class` to `ProfileAwarePdfTextExtractor::class`).
Every other part of the extraction lifecycle - page persistence, audit
logging, queue retry semantics, the FAILED/COMPLETED state machine - is
completely unaware anything changed.

## 6. Temp-File Security

**Not applicable - no temporary file is ever created.** Decryption happens
entirely against RawDataParser's already-parsed in-memory object map (section
5); the "private temp file, random name, restrictive permissions, guaranteed
cleanup" requirements this task anticipated are moot by construction rather
than satisfied by careful cleanup code. Verified directly, not just assumed:
`AesV2SecuredExtractionTest` snapshots `sys_get_temp_dir()` and this
project's `storage/app` tree before and after extraction (success path,
corrupt-file-exception path, and unsupported-profile-rejection path) and
asserts the directory listing is byte-for-byte identical - a stronger
guarantee than "created then cleaned up."

## 7. Memory Strategy

V1.5.4 measured **468.9MB peak (4.04x file size)** just to reach Smalot's
`/Encrypt` rejection point on the real 121,833,361-byte document - the basis
for `DocumentExtractionService`'s existing `RESOURCE_LIMIT` guard
(`MEMORY_ESTIMATE_MULTIPLIER = 4`).

Actually completing extraction is more expensive: decrypting every
string/stream AND building Smalot's full typed object graph for all 42,236
objects. Measured directly against the real document:

```
peak_memory        = 1074.1 MB  (memory_get_peak_usage(true))
file_size_bytes    = 121,833,361
peak / file_size ratio = 8.82
elapsed = 5.09s
```

**This exceeds the existing 4x guard's assumption** - a document that passed
`DocumentExtractionService`'s pre-flight check (correctly, for "will Smalot
at least be able to detect/reject it") could still hit an **uncatchable PHP
fatal** during the secured-extraction phase specifically, exactly the failure
mode every guard in this codebase exists to prevent.

**Fix: a second, separately-calibrated guard**, `SecuredPdfTextExtractor`'s
own `MEMORY_ESTIMATE_MULTIPLIER = 10` (padded above the measured 8.82x,
matching `DocumentExtractionService`'s own "deliberately conservative,
documented estimate, not a measured guarantee" precedent), checked against
file size **before** `SecuredPdfTextExtractor` does any work at all - this
runs after `ProfileAwarePdfTextExtractor` has already committed to the
secured path, so it costs nothing extra for any other document.
`DocumentExtractionService`'s original 4x guard is completely unchanged
(verified: no regression for unencrypted or fails-fast-unsupported
documents, which are the overwhelming majority of traffic).

**Verified empirically across the full range**, not just reasoned about:

| `memory_limit` | Outcome |
|---|---|
| 512M | `DocumentExtractionService`'s existing 4x guard already rejects this before any extractor call (`487MB estimated > 256MB budget`) - unchanged V1.5.3 behavior |
| 1024M | Same - existing 4x guard rejects (`487MB > 512MB`... margin is closer here; confirmed via direct fatal reproduction that 1024M is genuinely insufficient for the secured path, motivating the new guard) |
| 1500M | New 10x guard in `SecuredPdfTextExtractor` cleanly throws `RESOURCE_LIMIT` (no fatal) with 806.8MB actually used at the moment of rejection - this is the "passes the old guard, correctly caught by the new one" band the fix specifically targets |
| 3072M | Full extraction succeeds: 2639 pages, 1074.1MB peak, 5.09s |

No architecture change was made to reduce Smalot's own per-object
construction overhead (out of scope for V1.5.5 - it is inherent to Smalot's
object model for a document with this many objects, not specific to
encryption or to this milestone's own code).

## 8. Disk Strategy

Not applicable, for the same reason as section 6: there is no temporary
decrypted artifact on disk to size a preflight against. The only disk
activity during extraction is reading the original stored PDF (unchanged
from V1.5.3) and Laravel's normal page-row persistence (unchanged). The
original uploaded PDF is never modified - verified directly:
`AesV2SecuredExtractionTest::test_original_encrypted_fixture_remains_byte_for_byte_unchanged_after_extraction`
and, through the real persistence pipeline,
`MaintenanceDocumentExtractionTest::test_supported_aesv2_encrypted_pdf_completes_successfully_through_the_real_pipeline`
(asserts the stored file's bytes are identical after a full successful
extraction, not just after the extractor call in isolation).

## 9. Empty Password Boundary

The empty string is the only credential ever attempted, anywhere in this
codebase, for any document - not a policy choice enforced by convention, but
a structural fact: no method on `PdfSecurityInspector`,
`AesV2StandardSecurityHandler`, `SecuredPdfTextExtractor`, or
`ProfileAwarePdfTextExtractor` accepts a password parameter. There is no
password input UI, no stored PDF password, no password database column, no
password API parameter, and no code path that could be extended into a
brute-force loop without first changing a method signature (which none of
this milestone's tests would let pass unnoticed - see section 11,
`test_non_empty_user_password_document_fails_closed_without_ever_being_attempted`).

## 10. Failure Semantics

Unchanged classification taxonomy from V1.5.3/V1.5.4
(`PdfExtractionErrorCode`): every unsupported profile, malformed dictionary,
or authentication failure ends in `UNSUPPORTED_PDF_SECURITY` (permanent, no
retry burned - `ExtractMaintenanceDocumentJob` is completely unmodified).
Structurally broken/truncated files end in `INVALID_OR_CORRUPT_PDF`. A
document sized such that even the secured path's 10x estimate would not fit
the worker's `memory_limit` ends in `RESOURCE_LIMIT` (section 7) - never an
uncatchable fatal. No new error code was introduced; V1.5.5 needed none of
the "unnecessary schema churn" the task specifically warned against.

### Two real bugs found and fixed during this work (both were pre-existing Smalot behaviors, only ever triggered by genuinely encrypted content)

1. **Silent stream corruption via a Smalot-internal fallback.**
   `RawDataParser` unconditionally attempts to apply a stream's declared
   `/Filter` (e.g. `FlateDecode`) before any of this milestone's code ever
   sees the data. For encrypted content, that attempt is expected to fail
   and be silently ignored (`ignore_filter_decoding_errors` defaults `true`)
   - but its own fallback path (retrying via PHP's `compress.zlib://` stream
   wrapper) can misinterpret a few bytes of high-entropy AES ciphertext as
   the start of a valid deflate stream and return a short, **non-empty,
   incorrectly "decoded" result instead of throwing** - silently corrupting
   the token Smalot itself uses (`$part[3][0]`) for roughly 14% of the real
   document's 11,399 direct (non-object-stream) streams. Fixed by reading
   `$part[1]` (the raw pre-filter-decode extraction, populated by a
   completely separate code path that never invokes any filter) instead,
   with this project's own declared-`/Length` truncation replicating
   `RawDataParser`'s own convention for an exact, block-aligned ciphertext.
2. **Cross-reference streams are exempt from encryption entirely** (ISO
   32000-1 7.5.8.2 - same reasoning as the `/Encrypt` dictionary itself: a
   reader must be able to parse the xref stream before it can even
   authenticate). The real document's xref stream object carries its own
   `/ID` array (two 16-byte plaintext copies of the file ID, duplicating the
   trailer's own `/ID`) - attempting to AES-decrypt these correctly fails
   immediately (16 raw bytes cannot be a valid IV+ciphertext). Fixed by
   excluding any object whose `/Type` is `/XRef` from decryption entirely,
   alongside the `/Encrypt` object itself (already excluded from V1.5.4).

Neither of these appeared in fixture-only testing (the sanitized fixtures
were deliberately generated without object streams or xref streams, to
avoid an earlier, unrelated cosmetic Smalot warning documented in the
fixtures' own README) - **both were only discoverable against the real
document's actual structural complexity**, which is exactly why this task's
Section M (real local compatibility test, performed only after fixture
tests already passed) exists as a separate, later step rather than being
treated as optional.

## 13. Production Deployment Preconditions

Not evaluated or verified against Production in this milestone (no
deployment occurred), but explicitly required before a future V1.5.6-or-later
Production rollout of this capability:

- **The queue worker's actual PHP CLI `memory_limit` on Hostinger must be
  confirmed** (read-only `php artisan config:show` / `php -i`, no mutation)
  to comfortably exceed the threshold this milestone's guard now enforces
  for documents of this size class: for the real 121.8MB document
  specifically, `SecuredPdfTextExtractor`'s 10x guard estimates a
  ~1162MB peak and only permits the attempt when that is under 50% of
  `memory_limit`, i.e. `memory_limit >= ~2.3GB`; the measured true peak was
  1074.1MB, so `memory_limit >= ~1.2GB` would be the true minimum if the
  guard's safety margin were removed, but the guard as implemented (with its
  deliberate margin - section 7) is what actually runs, and 3072M was the
  smallest value this milestone actually verified succeeds end to end. If Production's current `memory_limit` is lower than the
  guard allows, the real document will continue to end in `RESOURCE_LIMIT`
  (safe, not a fatal) rather than `COMPLETED` until that is addressed - this
  is a real, known, currently-unverified gap between "the code works" and
  "Production is provisioned to run it," and is exactly what the next
  Production acceptance milestone must check first, before attempting real
  extraction there.
- Composer dependencies must be installed on Production exactly as recorded
  in `composer.lock` (`composer install --no-dev`, same procedure as every
  prior release) - `tecnickcom/tc-lib-pdf-encrypt` needs no special
  installation step beyond that.
- No `.env` change, no migration, no new capability/permission gate - this
  milestone requires none.
