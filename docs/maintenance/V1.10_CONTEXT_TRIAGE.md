# V1.10 - Knowledge Review Context Triage

## 1. Problem

After V1.9 (Source Page Context), a reviewer can read a group's full source page inside the
review UI - but only after opening it. With 705 distinct code groups (534 HIGH-evidence) and only
one (C-1127) reviewed so far, there was no way to tell from the LIST which groups are likely
self-contained and quick versus structurally likely to need a neighbouring page, without opening
every one of them.

## 2. The signal

`context_hint` (`SELF_CONTAINED` | `CONTEXT_RECOMMENDED`) and `context_reason`
(`PAGE_END_CONTINUATION` | `PAGE_START_CONTINUATION` | `null`), computed per group from where its
representative candidate's code text falls within its own source page, as a proportion of that
page's length. This document's own layout puts a code's content
(Code/Classification/Cause/Measures/Solution/...) *after* the code heading, so a match very near
the page's end means that content likely continues onto the next page; very near the start
suggests the group's context likely began on the previous page.

**It is purely structural.** It never implies a candidate is correct, good, safe, or accurate -
only that a reviewer may want to also read a neighbouring page (V1.9's Source Page Context /
adjacent-page tool) before deciding. No AI, no semantic parsing, no confidence score.

## 3. Real-data validation (not tuned to C-1127 alone)

Thresholds (`>= 0.75` near-end, `<= 0.10` near-start) were chosen by measuring, then confirmed
against the real Production import (705 groups, 534 HIGH-evidence) using the exact
representative-candidate selection `pageProvenance()` already uses (best evidence, then earliest
page):

| Bucket | Count | % |
|---|---|---|
| SELF_CONTAINED (mid-page) | 312 | 58.4% |
| CONTEXT_RECOMMENDED - PAGE_END_CONTINUATION | 79 | 14.8% |
| CONTEXT_RECOMMENDED - PAGE_START_CONTINUATION | 143 | 26.8% |

A genuinely useful, non-degenerate split - not "nearly everything flagged." Independently
confirmed against two real codes read directly during V1.9's acceptance: C-1124 and C-1125 sit on
the *same* source page (1459) - C-1124 classifies mid-page (matching its confirmed complete
Code..DIPSW section) while C-1125 classifies `>= 0.75` (matching its confirmed continuation onto
page 1460). C-1127 itself (representative page 1460) classifies `CONTEXT_RECOMMENDED` /
`PAGE_END_CONTINUATION` at ratio 0.847 - matching the real need that motivated V1.9 in the first
place.

## 4. Backend design

- No migration, no persisted state - purely derived on every request from data already stored
  (`maintenance_knowledge_entries` + `maintenance_document_pages`).
- List (`groups()`) and detail (`detail()`) both compute the hint via
  `KnowledgeCodeGroupQuery::contextHints()`: one bulk `maintenance_document_pages` fetch, keyed by
  page number, bounded to the current page's groups (never more than `per_page`, max 50) or the
  one group being viewed. Fetched text is used only to compute a position ratio in PHP and is
  discarded immediately - never serialized into the response.
- Fails safe to `SELF_CONTAINED` / `null` whenever the ratio cannot be determined (missing page,
  empty page, code not literally found on its own recorded page) - a malformed row must never
  produce a false "check the adjacent page" alarm.
- The `context` filter (`SELF_CONTAINED` | `CONTEXT_RECOMMENDED`), when applied, must compose
  correctly with pagination - it resolves matching codes across the *whole* import first
  (`codesMatchingContext()`), bounded by the import's own distinct representative pages (measured:
  352 pages / ~1.1MB for the real 705-group import, not the full 2639-page extraction), and runs
  only when a reviewer explicitly applies it - never on an ordinary list request.

## 5. Authorization / tenancy

Identical to every other Knowledge Review read: scoped to the already-authorized import's own
`document_id`, so a page (and therefore a classification) can never cross an account boundary.
Verified explicitly: two accounts with the same code on the same page number classify
independently from their own page text.

## 6. Frontend

- A small, subordinate badge ("Check context", `BookOpenCheck` icon) on a group's list row -
  **only** for `CONTEXT_RECOMMENDED`; the self-contained majority shows nothing extra, so the
  common case stays quiet.
- A `context` filter alongside the existing evidence/collision/review-state filters.
- The same hint, with its reason, optionally shown in the group detail header for consistency.
- Tooltip/help text on both surfaces states plainly: *"Describes document structure, not candidate
  correctness."*
- Review actions (approve/reject/restore/publish) and V1.9's Source Page Context are byte-for-byte
  unchanged.

## 7. Performance

Measured directly, not assumed: list requests add exactly one bulk query regardless of how many
groups are on the page (confirmed by a dedicated 1-group-vs-5-group query-count test). The
opt-in `context` filter's whole-import cost is bounded (352 pages / ~1.1MB in the real import) and
never approaches the full 2639-page extraction.

## 8. Release retention hardening (separate, deployment-tooling concern)

V1.9's own deployment hit a real Hostinger *account-level* disk quota (separate from the physical
filesystem, which had 8.6T free) after 56 release directories had accumulated with zero retention
mechanism - the oldest 46 were pruned by hand, with explicit operator approval, mid-deployment.
`scripts/deployment/prune-old-releases.sh` makes that routine: keeps the newest N releases plus
whichever one is currently active (regardless of its position in the ordering), defaults to a dry
run, fails closed on any path that doesn't look like `.../a3-production-app/releases`, and only
ever runs **after** activation + smoke + acceptance have already passed for a new release - never
before, never as part of activation itself. See `docs/production/RELEASE_PROCEDURE.md` step 20.
