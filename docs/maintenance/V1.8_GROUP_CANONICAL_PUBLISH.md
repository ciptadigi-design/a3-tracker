# V1.8 - Group-Aware Canonical Review & Single-Code Publish

## 1. Problem

V1.7.2 made review code-centred, but publishing was still per candidate. The legacy
`MaintenanceKnowledgePublishService` upserts `machine_error_codes` by
`(account, machine model, code)` with **last-writer-wins**, writes `operator_description` from an
`operator_solution` the detector never fills, and copies the detector's title. On the real import 78%
of candidate titles are the detector's generic fallback `Error Code C-XXXX` (2101 of 2680), so
publishing occurrences one by one would let candidate order decide the catalog text and would
publish placeholder titles.

## 2. Domain rule

The **normalized error-code group** is the review-to-publish unit. One group publishes as exactly
one logical publication in one transaction:

| Catalog artefact | Source |
|---|---|
| ONE `machine_error_codes` row | the reviewer's canonical title / description (cause) / operator guidance |
| 0..1 `maintenance_error_solutions` step (`requires_technician`) | the reviewer's technician solution |
| N `maintenance_document_references` | one per **unique supporting source page** (provenance) |

Supporting occurrences are provenance only. Nothing is AI-generated and nothing is chosen for the
reviewer: the canonical occurrence is selected explicitly (the UI only *labels* the strongest-evidence,
earliest-page occurrence as "Suggested"), and every field is written or confirmed by a human.

## 3. Data model

**No migration, no new table or column.** The reviewer's canonical content travels in the request and
is bound to a signed preview token; every server-side fact (collision, supporting pages, existing
record) is recomputed at preview **and** at publish, inside a transaction that row-locks the group and
any existing catalog record. Publishing marks **only the canonical row** (`APPROVED`, `approved_by`,
`published_at`); supporting occurrences and all candidate text are left untouched, so the V1.7.2
derived group state becomes `PUBLISHED` with no fake per-row mutation.

Group workflow state: only `PUBLISHED` is server-derived (a published occurrence exists). `UNREVIEWED`
/ `IN_REVIEW` / `READY_TO_PUBLISH` describe the reviewer's local progress and are deliberately not
persisted (no workflow engine).

## 4. Endpoints (under `/api/v1/maintenance/document-imports/{id}/code-groups/{code}`)

| Endpoint | Access | Purpose |
|---|---|---|
| `GET .` (V1.7.2) | member | now also returns `publication` (published?, suggested canonical + title, supporting pages, server collision) and `title_is_placeholder` per occurrence |
| `POST publish-preview` | `canManageCatalogScope` | authoritative, read-only preview + short-lived token |
| `POST publish` | `canManageCatalogScope` | the single-code publish; needs the token |

There is no bulk, batch or publish-all route (asserted by a test that enumerates every `publish` route).
Legacy `POST knowledge-entries/{id}/publish` is **refused (409 `GROUP_PUBLISH_REQUIRED`) for
PDF-derived candidates** (`PDF_EXTRACTION` with a `normalized_code`) and unchanged for manual entries;
the legacy service itself is unchanged apart from making `advanceImportStatusIfComplete` public.

## 5. Placeholder guard

`PlaceholderTitle` follows the detector convention: every error-code token (`C-3102`, `C3102`,
`C - 3102`, any code) is stripped, then everything that is not a letter or digit; the title is a
placeholder only if nothing informative is left (`Error Code`, `Code`, `Untitled`, nothing).
`Error Code C-3102` / `C-3102` are rejected with "Review and replace the placeholder title before
publishing."; `C-3102 Fuser temperature abnormal` and `Fuser error (C-3102)` are accepted. Also
required: at least one of description / operator guidance / technician solution.

## 6. Preview and publish semantics

- **Provenance** - supporting occurrences = every non-`REJECTED` occurrence; pages = each
  occurrence's `start..end` (capped at a 20-page span), de-duplicated and sorted; one reference per
  unique page, `page_number` only, no page text.
- **Collision (server-recomputed)** - `NEW` (no record for account + import machine model + code),
  `EXISTING` (a record with content), `POTENTIAL_UPDATE` (a record that is still empty). The V1.6
  candidate snapshot is not trusted.
- **Existing record** - never touched without explicit confirmation: publish needs
  `confirm_update=true` (422 otherwise). Update writes only *provided* fields (a blank field never
  blanks an existing value), appends a solution step only if no step has the same text, and adds only
  missing page references. The preview lists exactly which fields would change.
- **Token** - stateless HMAC (`PreviewToken`, same pattern as V1.7.2, domain-separated) over import,
  code, acting user, canonical id, a hash of the content, a fingerprint of the group's rows plus the
  existing record (content, solution/reference counts), and a 15-minute expiry.

| Situation | Result |
|---|---|
| forged / tampered / mismatched (content, canonical, code, user) token | 422 |
| group or existing record changed since preview; expired (nothing published yet) | 409 `STALE_PREVIEW` |
| canonical occurrence rejected | preview `can_publish=false`; publish 409 |
| canonical not in this group (other group / import / account) | 422 |
| placeholder title / no content | 422 |
| already published, identical content | **200 idempotent success, no writes, no audit** |
| already published, different content | 409 (changing published knowledge needs a future update flow) |

Idempotency is decided **before** staleness, so a double click or a retry after a successful publish
(even with an expired token) is a success, never a conflict, and never a duplicate code, step,
reference or audit row.

## 7. Audit

`maintenance_knowledge_group.published` (target = the import): `normalized_code`,
`canonical_candidate_id` (one id), `occurrence_count`, `supporting_page_count`, `collision_status`,
`publish_mode` (`created`/`updated`), 16-char `publication_fingerprint`. Five allowlist entries were
added to `GovernanceAudit::FIELDS`. The existing `machine_error_code.published_from_import` event is
reused (records the short title label as before; descriptions and solutions are never in it). No
candidate/solution prose, no ID list, no token, no path (asserted by tests).

## 8. Frontend

Group detail now has: a header (best evidence, collision, review state, workflow state, occurrences,
supporting page count); occurrences with **Use as canonical** (nothing pre-selected; "Suggested" is only
a label; the selected occurrence is visibly marked); a **Canonical knowledge** editor (code read-only;
title, description/cause, operator guidance, technician solution; live placeholder validation; explicit
"Use suggested title" and "Start from the stored excerpt" buttons - nothing is copied silently);
**Supporting evidence** (unique pages); and **Review Publish**, which opens a read-only preview dialog
showing code, title, canonical source page, occurrences, pages, catalog state, exactly what will be
written, an update warning + acknowledgement for existing records, and the final **Publish Knowledge**
button. A stale/invalid confirmation says nothing changed and offers "Preview again". A published group
shows a Published banner and offers no way to publish again. The per-occurrence Publish button is gone
from the group detail and, for PDF-derived candidates, from the flat list ("Publish from its code
group"). V1.7.2 triage and the V1.7 ID selection are unchanged.

## 9. Real-data read-only validation (Production, aggregates only)

- `C-3102`: 8 occurrences (LOW x4, MEDIUM x2, HIGH x2), all single-page on 8 distinct pages, all
  DRAFT / unpublished / NEW -> 8 supporting pages, no de-duplication needed.
- Page spans: max 1, no inverted or null ranges.
- Catalog empty (0 codes, 0 solutions, 0 references); the import has a machine model and the document
  an account, so the `(account, model, code)` scoping is exercised in real use.
- 2101 / 2680 candidate titles are the exact detector fallback -> the guard will block them; the other
  579 detector titles pass the guard and are the reviewer's judgement (the guard is deliberately
  conservative and only rejects the generic placeholder).

Nothing was written and nothing was published.

## 10. Not in this milestone

Bulk / batch / publish-all, AI-generated content, updating an already-published group, a merge engine
for existing records, group draft persistence, any migration, any deployment.
